## Before going live

- **Set `NUXT_APP_SECRET`** to a random string of at least 32 characters. It seals sessions; anyone who has it can forge them. Changing it signs everyone out.
- **Serve over HTTPS.** Session cookies are `Secure`, so browsers send them only over HTTPS (or to `localhost`).
- **Set `NUXT_PUBLIC_ATELIER_SITE_URL`** to your public URL. Passkeys belong to its domain, and requests from it are accepted as same-site.
- **Behind a proxy or load balancer,** set `auth.trustProxy: true` so sign-in limits see each visitor's IP rather than the proxy's. Leave it off otherwise: clients could fake their address.
- **Finish first-run setup** right after deploying. Until the first administrator exists, anyone who reaches the setup endpoint can become it.
- **Keep exports private.** An [export](/deployment/backup) holds password hashes.

## What's built in

| Threat | Protection |
|---|---|
| Stolen database | passwords hashed with scrypt; sessions stored only as hashes of their ids |
| Stolen session cookie | sealed, `HttpOnly`, `Secure`, `SameSite=Lax`; signing out or a password change revokes it on the server |
| Password guessing | [sign-in limits](/reference/authentication#sign-in-limits) per email and IP, shared by every server instance |
| Cross-site request forgery | `Sec-Fetch-Site` and `Origin` checks, plus a per-session token on every signed-in write ([details](/reference/authentication#calling-the-api-from-your-own-code)) |
| Locking yourself out | the last administrator can't be demoted or deleted |
| Privilege escalation | only administrators grant the admin role; nobody changes their own role |
| Unnoticed changes | an [audit log](/reference/authentication#the-audit-log) of sign-ins, failures, user and role changes |

## Roles

Give each person the [role](/reference/permissions) they need, and few people `users` or `roles`: someone who can edit roles can give their own role more.
