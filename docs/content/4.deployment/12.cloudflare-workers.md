---
title: Cloudflare Workers
description: Run Nuxt Atelier on Cloudflare Workers with a D1 database and R2 for uploads, and what D1 can't do.
---

Nuxt Atelier runs on Cloudflare Workers with [D1](https://developers.cloudflare.com/d1/) as its database and R2 for uploads, since a Worker has no disk. D1 is SQLite, so your content, schema and migrations work unchanged, with the limitations below.

## Build command and preset

The preset is `cloudflare-module`, set in `nuxt.config.ts` (or `NITRO_PRESET=cloudflare-module` at build). Create the database once, and put its id in `wrangler.json`:

```bash
npx wrangler d1 create my-site
```

Then build and deploy:

```bash
npm run build
npx wrangler deploy
```

## Configuration files

<!-- file: cloudflare-workers/nuxt.config.ts -->
```ts [nuxt.config.ts]
// Cloudflare Workers: the cloudflare-module preset, D1 as the database, and uploads in R2 through its S3 API
// (npm install @nuxt-atelier/storage-s3). A Worker has no disk.
export default defineNuxtConfig({
  modules: ['nuxt-atelier', '@nuxt-atelier/admin', '@nuxt-atelier/storage-s3'],
  compatibilityDate: '2026-10-01',
  nitro: { preset: 'cloudflare-module' },
  atelier: {
    database: { url: 'd1:DB' }, // the binding name in wrangler.json
    migrations: { autoApply: true }, // `atelier migrate apply` can't reach D1
    storage: { driver: 's3' },
  },
})
```

<!-- file: cloudflare-workers/wrangler.json -->
```json [wrangler.json]
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "my-site",
  "main": ".output/server/index.mjs",
  "compatibility_date": "2026-10-01",
  "compatibility_flags": ["nodejs_compat"],
  "assets": { "directory": ".output/public", "binding": "ASSETS" },
  "d1_databases": [
    { "binding": "DB", "database_name": "my-site", "database_id": "<your D1 database id>" }
  ],
  "triggers": { "crons": ["* * * * *"] },
  "vars": {
    "NUXT_PUBLIC_ATELIER_SITE_URL": "https://example.com",
    "NUXT_ATELIER_S3_ENDPOINT": "https://<account id>.r2.cloudflarestorage.com",
    "NUXT_ATELIER_S3_BUCKET": "media",
    "NUXT_ATELIER_S3_REGION": "auto"
  }
}
```

Install the storage driver in your app: `npm install @nuxt-atelier/storage-s3`. A `d1:` build bundles only the D1 driver, so the Worker stays small.

## Environment variables

Settings that aren't secret go in `wrangler.json`'s `vars`. Secrets go in with `wrangler secret put`, before the first deploy:

```bash
npx wrangler secret put NUXT_APP_SECRET
npx wrangler secret put NUXT_ATELIER_S3_ACCESS_KEY_ID
npx wrangler secret put NUXT_ATELIER_S3_SECRET_ACCESS_KEY
npx wrangler secret put NUXT_ATELIER_AUTH_SETUP_TOKEN
```

| Variable | Where | Value |
|---|---|---|
| `NUXT_APP_SECRET` | secret | at least 32 random characters (`openssl rand -hex 32`). A Worker's secrets arrive with each request, so it can't check this one at startup: set it before deploying. |
| `NUXT_ATELIER_AUTH_SETUP_TOKEN` | secret | optional: first-run setup asks for it, so nobody else can become the first administrator |
| `NUXT_ATELIER_S3_ACCESS_KEY_ID`, `NUXT_ATELIER_S3_SECRET_ACCESS_KEY` | secret | an R2 API token's keys |
| `NUXT_ATELIER_S3_ENDPOINT`, `_BUCKET`, `_REGION` | `vars` | the R2 bucket; the region is `auto` |
| `NUXT_PUBLIC_ATELIER_SITE_URL` | `vars` | the site's public URL |

## Database

D1, through the `DB` binding (`database.url: 'd1:DB'`). Generate migrations for SQLite during development (`nuxt dev` on a local SQLite file does it for you) and commit them. They're bundled into the Worker.

### D1 and transactions

D1 has no interactive transactions: it runs a list of statements atomically (`batch()`), but code can't read and decide in the middle of one. Nuxt Atelier works around this where it can, and refuses where it can't:

| Operation | On D1 |
|---|---|
| Saving content | One atomic batch. Every save writes a revision numbered by version, and two revisions can't share a number, so a save that lost a race to a newer one rolls back as a whole. You get the same `409` as on other engines. |
| Deleting content | One atomic batch, with every relation's `onDelete` applied. The references are read just before the batch runs, so one added in that moment is left pointing at nothing (it reads as `null`). |
| Applying migrations | One atomic batch, on the first CMS write after a deploy (`autoApply`). `atelier migrate apply` can't reach a D1 database. |
| Importing an export | Not supported: it needs a transaction. |
| Your own code using `withTransaction(await useAtelierDatabase(), 'What it does', fn)` | Refused with `UnsupportedOperationError`, naming the operation, before anything changes. |

## Migrations on deploy

`migrations.autoApply`: the Worker applies pending migrations in one batch, on the first CMS write after a deploy. They aren't applied when the Worker starts because Workers only see their bindings inside a request.

## Media storage

R2, through its S3-compatible API ([S3-compatible storage](/reference/media#s3-compatible-storage-and-cloudflare-r2)). Create a bucket and an R2 API token for it, and put the token's keys in secrets. The bucket can stay private: your app serves the files.

`sharp` can't run on Workers, so image variant URLs serve the original. To resize images, use an [image service](/reference/media#image-services) such as Cloudflare Image Resizing.

## Scheduled jobs

A Cron Trigger runs background jobs: `triggers.crons` in `wrangler.json` holds `jobs.schedule` (every minute by default). Keep them the same when you change the schedule. With `nitro.cloudflare.deployConfig`, Nitro generates the wrangler config and adds the trigger itself.

## Real-time

The admin's WebSocket is served by the Worker. Changes are pushed to editors connected to the same isolate; changes made through other isolates arrive with the admin's 60-second poll.

## Limitations

| Limitation | Instead |
|---|---|
| No disk: local uploads are lost | R2, or other S3-compatible storage |
| No `sharp`: image variant URLs serve the original | an [image service](/reference/media#image-services), such as Cloudflare Image Resizing, in `media.provider` |
| `atelier migrate apply` and its `--dry-run` can't reach D1 | `migrations.autoApply`; rehearse migrations on a local SQLite copy of the data |
| Importing an export isn't supported | import into SQLite or PostgreSQL on a platform with a server |
| `withTransaction` in your own code is refused | SQLite, PostgreSQL, MySQL or MariaDB, which have transactions, on a platform with a server |
| SMTP email (`smtp://`) can't be sent from a Worker | `resend://` or `postmark://` in `NUXT_ATELIER_MAIL_URL` |
| Real-time pushes reach only the same isolate; others wait for the 60-second poll | a platform with a server, like [Docker](/deployment/docker), for changes pushed at once |

## Local development

`nuxt dev` uses a local SQLite file by default, which behaves like D1 for content. To run the built Worker locally against a local D1:

```bash
npx nuxi build
npx wrangler dev .output/server/index.mjs --assets .output/public
```
