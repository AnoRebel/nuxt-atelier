## Health checks

Two endpoints, neither cached and neither needing a session:

| Endpoint | Answers |
|---|---|
| `GET /api/_atelier/health/live` | `200 { "status": "ok" }` while the server answers. Checks nothing else. |
| `GET /api/_atelier/health/ready` | `200` when the server can do its work, `503` when the database is unreachable or has pending migrations |

Point a liveness probe at `live` and a readiness probe (or a load balancer's health check) at `ready`. A database outage then takes the instance out of rotation without restarting it, which wouldn't help.

`ready` reports each check:

```json
{
  "status": "ready",
  "checks": {
    "database": "ok",
    "migrations": { "pending": 0 },
    "storage": "ok",
    "jobs": { "failed": 0 }
  }
}
```

A check that fails, or takes more than 3 seconds, reads `"error"`. The response never holds the reason, which can include a connection string. The reason goes to the server log. Storage and failed jobs are reported without affecting the status: a site can serve pages while its media storage is down, and failed jobs need someone to look at them, not a restart.

## Shutting down

When the server is asked to stop (`SIGTERM` or `SIGINT` on the Node, Bun and Deno presets), Nuxt Atelier stops starting background jobs. The running ones get 10 seconds to finish. Any still running after that go back in the queue, due at once, and the attempt isn't counted, so they aren't marked failed. The next instance, or this one restarted, runs them. Then the database connection is closed.

Give the platform's stop timeout a little more than 10 seconds, so the server isn't killed before it's done.
