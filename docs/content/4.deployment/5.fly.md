[Fly.io](https://fly.io) runs the [Docker guide's](/deployment/docker) image on a Machine. A volume keeps SQLite and the uploads across deploys.

## Build command and preset

The preset is Nuxt's default, the Node server, built by the Docker guide's `Dockerfile`: copy it and its `.dockerignore` into your app. Fly builds the image on each deploy. The first time, create the app and its volume, and set the secrets:

```bash
fly apps create my-site
fly volumes create atelier_data --size 1 --region ams
fly secrets set NUXT_APP_SECRET=$(openssl rand -hex 32) NUXT_ATELIER_AUTH_SETUP_TOKEN=$(openssl rand -hex 16)
fly deploy --ha=false
```

Then `fly deploy` for each new version.

## Configuration files

<!-- file: fly/fly.toml -->
```toml [fly.toml]
# Nuxt Atelier on Fly.io: one Machine, with SQLite and uploads on a volume. Uses the Dockerfile of the Docker guide.
app = "my-site"
primary_region = "ams"
# running jobs get 10 seconds to finish on SIGTERM
kill_signal = "SIGTERM"
kill_timeout = 15

[build]
  dockerfile = "Dockerfile"

[env]
  NUXT_PUBLIC_ATELIER_SITE_URL = "https://my-site.fly.dev"
  # Fly's proxy sets X-Forwarded-For
  NUXT_ATELIER_AUTH_TRUST_PROXY = "true"

[http_service]
  internal_port = 3000
  force_https = true
  # keep the Machine running: background jobs run in the server process
  auto_stop_machines = "off"
  auto_start_machines = true
  min_machines_running = 1

  [[http_service.checks]]
    grace_period = "10s"
    interval = "30s"
    method = "GET"
    timeout = "5s"
    path = "/api/_atelier/health/ready"

[mounts]
  source = "atelier_data"
  destination = "/app/.data"
```

## Environment variables

Secrets go in with `fly secrets set`, the rest in `fly.toml`'s `[env]`:

| Variable | Where | Value |
|---|---|---|
| `NUXT_APP_SECRET` | secret | at least 32 random characters. The server won't start without it. |
| `NUXT_ATELIER_AUTH_SETUP_TOKEN` | secret | optional: first-run setup asks for it, so nobody else can become the first administrator |
| `NUXT_PUBLIC_ATELIER_SITE_URL` | `[env]` | the site's public URL |
| `NUXT_ATELIER_AUTH_TRUST_PROXY` | `[env]` | `true`: requests arrive through Fly's proxy |

The image sets the database and upload paths, in the volume.

## Database

SQLite, in `/app/.data/atelier.sqlite` on the `atelier_data` volume. For PostgreSQL, install `pg` in your app, set `NUXT_ATELIER_DATABASE_URL` to the database's URL as a secret, and rebuild.

## Migrations on deploy

The image sets `NUXT_ATELIER_MIGRATIONS_AUTO_APPLY=true`: the server applies pending migrations when it starts. A `release_command` can't apply them on SQLite: Fly runs it on a temporary Machine without the volume.

## Media storage

Uploads go to `/app/.data/uploads`, on the volume.

## Scheduled jobs

Background jobs run in the server process, on Nitro's scheduler. `auto_stop_machines = "off"` keeps the Machine running, so jobs (scheduled publishing, emails) run on time instead of waiting for the next visitor. `kill_timeout = 15` gives running jobs their 10 seconds to finish at a deploy.

## Real-time

The server serves the admin's WebSocket itself, through Fly's proxy: edits, locks and comments are pushed to other editors at once.

## Limitations

| Limitation | Instead |
|---|---|
| A volume belongs to one Machine: a second Machine would get its own database and uploads | PostgreSQL for the database and [S3-compatible storage](/reference/media#s3-compatible-storage-and-cloudflare-r2) for uploads, then more Machines |
| A stopped Machine runs no jobs | keep `auto_stop_machines = "off"`, or call the [trigger endpoint](/reference/jobs#the-trigger-endpoint) from a scheduler |
| `release_command` has no volume, so it can't migrate SQLite | `NUXT_ATELIER_MIGRATIONS_AUTO_APPLY`, as the image sets |
