## What a page costs

Nuxt Atelier aims to add little to the sites it runs:

- **In the browser:** at most 15 KB gzip of a public page's JavaScript comes from Nuxt Atelier, and none from the admin, the visual editor or AI assist. A plain page today loads about 1.5 KB of ours. `test/budget/client-js.test.ts` checks it on every change, by source map on a real page.
- **On the server:** a cached page in at most 50 ms p95, and an uncached page of 50 blocks in at most 200 ms p95. `scripts/bench.ts` measures both and fails CI over those budgets, or when a run is more than 10% slower than the median of the last ten on `main`. On a laptop, about 1 ms and 15 ms.
- **In the database:** reading an entry takes the same number of queries with 20 blocks or 200, and with 2 relations or 20 (at most 12; a list, 14).
- **In memory:** exports, imports, uploads and downloads stream. A 150 MB export, or a 200 MB upload, holds a few megabytes at a time.

## Caching

Two caches sit in each server's memory. Any content write clears both, on that instance.

| Cache | What it holds | Configure |
|---|---|---|
| Content | what the site's routes resolve to, for visitors | `limits.cacheSize` entries (`0`: none); 30 seconds at most |
| Rendered pages | whole HTML pages, for visitors | `cache.pages` seconds (`0`, the default: none) |

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  atelier: { cache: { pages: 60 } }, // or NUXT_ATELIER_CACHE_PAGES=60
})
```

A page is kept only when it can be anyone's: a GET with no `_atelier`, `draft` or `preview` in its query, from a visitor (a request with cookies counts only if they don't sign anyone in), answered `200` without setting a cookie. Pages served from it carry `x-atelier-cache: hit`. Every other render, a signed-in editor's, a draft, a shared preview link, the visual editor's frame, is sent `cache-control: private, no-store`, so neither this cache nor a CDN keeps it.

**Several instances:** each keeps its own caches, and a write clears only the one it reached. Another instance shows the change when its cached copy expires: within 30 seconds for content, `cache.pages` for pages. Keep `cache.pages` short when you run several, or clear them yourself, as below.

**A CDN in front:** cache what visitors get (it carries no `private`), and purge when content changes. The `atelier:content:changed` server hook fires after every committed write, with what changed:

```ts [server/plugins/purge.ts]
import { useServerHooks } from 'nuxt/server'

export default () => {
  useServerHooks().hook('atelier:content:changed', async ({ type, id, live }) => {
    if (live)
      await purgeMyCdn(type, id) // your CDN's purge API: everything, or the pages showing this entry
  })
}
```

Nitro's own `routeRules` caching (`swr`, `isr`) doesn't know who's signed in: don't apply it to pages editors preview. `cache.pages` does the same job for visitors and leaves editors alone.

## Limits and settings to tune

Every server operation has a limit, checked at startup: a runtime override outside its range (`NUXT_ATELIER_LIMITS_*`) stops the server with a message. The full list, with ranges and defaults, is in the [configuration reference](/reference/configuration#limits). The ones that matter for performance:

- **`limits.dbPoolSize`** (10): connections per instance. Raise it with traffic, within what your database allows across all instances.
- **`limits.cacheSize`** (1,000): routes kept in memory per instance. Each is one route's entry, so a site with more pages than this gets more cache misses.
- **`limits.maxRelationDepth`** (3) and **`limits.maxPageSize`** (100): the most a single API request can make the server load.
- **`limits.jobConcurrency`** (4): background jobs at once: webhook deliveries, pruning old revisions and form submissions, and your own.
- **`limits.maxBodySize`** and **`limits.maxUploadSize`**: the largest JSON body and upload.

Images are resized once per width and kept: let a CDN cache `/api/_atelier/media-files/…`, which public files serve with `max-age` of a year.
