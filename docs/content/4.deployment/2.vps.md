---
title: Node on a VPS
description: Run Nuxt Atelier on your own server with Node, systemd and Caddy, with SQLite and uploads on its disk.
---

A server of your own runs everything Nuxt Atelier does: SQLite and uploads on its disk, background jobs and the admin's real-time connection in the server process. systemd keeps the server running, and [Caddy](https://caddyserver.com) serves it over HTTPS.

The examples assume the app is checked out in `/srv/atelier`, run by a system user `atelier`, with Node 24 or 26 installed.

## Build command and preset

The preset is Nuxt's default, the Node server: nothing to set. Build on the server, in the checkout:

```bash
npm ci
npm run build
sudo systemctl restart atelier
```

The server is `.output/server/index.mjs`. Run these again for each new version.

## Configuration files

The app's config only adds `trustProxy`, since Caddy sits in front:

<!-- file: vps/nuxt.config.ts -->
```ts [nuxt.config.ts]
// A VPS: Nuxt's default Node server behind Caddy, run by systemd. Settings come from /srv/atelier/.env.
export default defineNuxtConfig({
  modules: ['nuxt-atelier', '@nuxt-atelier/admin'],
  compatibilityDate: '2026-10-01',
  atelier: {
    auth: { trustProxy: true }, // Caddy sets X-Forwarded-For
  },
})
```

The systemd unit runs the server, and applies migrations before it starts:

<!-- file: vps/atelier.service -->
```ini [atelier.service]
# /etc/systemd/system/atelier.service: the site built in /srv/atelier, run as the user atelier.
[Unit]
Description=Nuxt Atelier
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=atelier
Group=atelier
WorkingDirectory=/srv/atelier
EnvironmentFile=/srv/atelier/.env
# apply pending migrations before the new version starts
ExecStartPre=/srv/atelier/node_modules/.bin/atelier migrate apply
ExecStart=/usr/bin/node .output/server/index.mjs
Restart=on-failure
# running jobs get 10 seconds to finish on SIGTERM
KillSignal=SIGTERM
TimeoutStopSec=15

[Install]
WantedBy=multi-user.target
```

Caddy gets a certificate for your domain and passes requests to the server:

<!-- file: vps/Caddyfile -->
```text [Caddyfile]
# /etc/caddy/Caddyfile: HTTPS for the site, with a certificate Caddy gets and renews itself
example.com {
	reverse_proxy 127.0.0.1:3000
}
```

Install them once:

```bash
sudo useradd --system --home-dir /srv/atelier atelier
sudo chown -R atelier:atelier /srv/atelier
sudo cp atelier.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now atelier
sudo cp Caddyfile /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

## Environment variables

systemd reads them from `/srv/atelier/.env` (`EnvironmentFile`); the built server doesn't read `.env` files itself:

<!-- file: vps/.env.example -->
```bash [.env.example]
# /srv/atelier/.env, read by systemd (EnvironmentFile). `openssl rand -hex 32` makes a secret.
NODE_ENV=production
HOST=127.0.0.1
PORT=3000
NUXT_APP_SECRET=
NUXT_PUBLIC_ATELIER_SITE_URL=https://example.com
NUXT_ATELIER_DATABASE_URL=file:/srv/atelier/.data/atelier.sqlite
NUXT_ATELIER_STORAGE_DIR=/srv/atelier/.data/uploads
# First-run setup asks for this token until the first administrator exists
NUXT_ATELIER_AUTH_SETUP_TOKEN=
```

| Variable | Value |
|---|---|
| `NUXT_APP_SECRET` | at least 32 random characters (`openssl rand -hex 32`). The server won't start without it. |
| `NUXT_PUBLIC_ATELIER_SITE_URL` | the site's public URL |
| `NUXT_ATELIER_DATABASE_URL` | the SQLite file, by absolute path |
| `NUXT_ATELIER_STORAGE_DIR` | where uploads go |
| `NUXT_ATELIER_AUTH_SETUP_TOKEN` | optional: first-run setup asks for it, so nobody else can become the first administrator |
| `HOST`, `PORT` | where the server listens: only on `127.0.0.1`, for Caddy |

Keep the file readable by `atelier` alone: `sudo chmod 600 /srv/atelier/.env`.

## Database

SQLite, in `/srv/atelier/.data/atelier.sqlite`: nothing to install or run. For PostgreSQL, MySQL or MariaDB instead, install the engine's driver (`npm install pg`, or `mysql2`), set `NUXT_ATELIER_DATABASE_URL` to its URL, and rebuild. See [Database](/reference/database).

## Migrations on deploy

The unit's `ExecStartPre` runs `atelier migrate apply` before each start, so a new version starts on an up-to-date database. If a migration fails, the server doesn't start. To catch that before it happens, rehearse against the production database first:

```bash
sudo -u atelier sh -c 'set -a; . /srv/atelier/.env; cd /srv/atelier && npx atelier migrate apply --dry-run'
```

## Media storage

Uploads go to `/srv/atelier/.data/uploads` on the server's disk. Back that directory up with the database: see [backup](/deployment/backup).

## Scheduled jobs

Background jobs run in the server process, on Nitro's scheduler, every minute by default (`jobs.schedule`). Nothing to set up. On `systemctl stop` or a restart, running jobs get 10 seconds to finish; the unit's `TimeoutStopSec=15` leaves them that time.

## Real-time

The admin's real-time connection is a WebSocket the server serves itself. Caddy's `reverse_proxy` passes WebSocket connections through, so edits, locks and comments are pushed to other editors at once.

## Limitations

| Limitation | Instead |
|---|---|
| One server: a second one can't share the SQLite file or the uploads directory | PostgreSQL, MySQL or MariaDB for the database, and [S3-compatible storage](/reference/media#s3-compatible-storage-and-cloudflare-r2) for uploads |
| A migration that fails keeps the new version from starting | rehearse with `atelier migrate apply --dry-run` against the production database before deploying |
