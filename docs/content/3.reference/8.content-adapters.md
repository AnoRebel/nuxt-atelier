The admin and the visual editor never touch the database directly. They load, change and save content through a **content adapter**. The built-in one stores content in your database; an adapter of your own can keep it anywhere: another CMS, a headless API, files in a repository.

The contract is published from `nuxt-atelier/adapter` and versioned. This release implements contract **1**.

## The contract

An adapter is an object with these operations:

| Operation | Required | Does |
|---|---|---|
| `loadEditState(ref, context?)` | yes | the content to edit: `{ ref, version, data }`. `version` is `null` for content never saved |
| `getFieldConfig(ref)` | yes | the fields, as JSON-safe [field descriptors](/reference/fields) |
| `listBlockTypes()` | yes | the block types the editor offers |
| `addBlock(state, at, block, index?)` | yes | returns a new state with the block inserted |
| `moveBlock(state, id, to, index?)` | yes | returns a new state with the block moved |
| `updateBlock(state, id, props)` | yes | returns a new state with the props merged in |
| `deleteBlock(state, id)` | yes | returns a new state without the block |
| `save(state, context?)` | yes | persists and returns the saved state; a stale state is refused with a `409` |
| `permissions(ref, context?)` | yes | `{ read, update }` for the current user |
| `revisions.list(ref)`, `revisions.load(ref, version)` | no | the content's history |

- **`ref`** says what's edited: `{ kind: 'collection', name, id? }` (no `id` for a new entry) or `{ kind: 'singleton', name }`.
- **Block locations:** `at` and `to` are `{ field }` for a blocks field, or `{ parent, area }` for a nested area of a block.
- **Errors** carry an HTTP status in `statusCode`. A stale save also carries `data.currentVersion`, so the editor can offer to reload.

### Capabilities

`defineContentAdapter()` checks an adapter before it's used:

- it refuses an adapter written for another contract version, naming both versions;
- it names any missing required operation;
- it adds `capabilities`, which says which optional features the adapter has, for example `{ revisions: false }`.

The admin and the editor read `capabilities` and hide what's missing: with no revision operations there's no history panel, and no revision calls are made.

## Block operations

The four block operations rarely need backend logic. `blockOperations` implements them on an edit state, never mutating the one it gets:

```ts
import { blockOperations } from 'nuxt-atelier/adapter'

addBlock: async (state, at, block, index) => blockOperations.add(state, at, block, index),
```

They refuse an unknown block id, a duplicate id, or moving a block into itself, with a `400`.

## Example: a headless CMS backend

This adapter edits documents stored in a REST API. Its API uses an `If-Match` header for optimistic locking and answers `412` when a document changed:

```ts [server/utils/acme-adapter.ts]
import type { ContentRef, EditState } from 'nuxt-atelier/adapter'
import { blockOperations, CONTENT_ADAPTER_CONTRACT, defineContentAdapter } from 'nuxt-atelier/adapter'

export function createAcmeAdapter(baseURL: string, token: string) {
  const api = $fetch.create({ baseURL, headers: { authorization: `Bearer ${token}` } })
  const path = (ref: ContentRef) => ref.kind === 'singleton' ? `/singletons/${ref.name}` : `/collections/${ref.name}/${ref.id ?? ''}`

  return defineContentAdapter({
    contract: CONTENT_ADAPTER_CONTRACT,
    name: 'acme',

    async loadEditState(ref) {
      if (ref.kind === 'collection' && !ref.id)
        return { ref, version: null, data: {} }
      const doc = await api<{ revision: number, fields: Record<string, unknown> }>(path(ref))
      return { ref, version: doc.revision, data: doc.fields }
    },
    getFieldConfig: ref => api(`/schemas/${ref.name}`),
    listBlockTypes: () => api('/block-types'),

    addBlock: async (state, at, block, index) => blockOperations.add(state, at, block, index),
    moveBlock: async (state, id, to, index) => blockOperations.move(state, id, to, index),
    updateBlock: async (state, id, props) => blockOperations.update(state, id, props),
    deleteBlock: async (state, id) => blockOperations.delete(state, id),

    async save(state: EditState) {
      try {
        const doc = await api<{ id: string, revision: number, fields: Record<string, unknown> }>(path(state.ref), {
          method: state.version === null ? 'POST' : 'PUT',
          headers: state.version === null ? {} : { 'if-match': String(state.version) },
          body: { fields: state.data },
        })
        const ref = state.ref.kind === 'collection' ? { ...state.ref, id: doc.id } : state.ref
        return { ref, version: doc.revision, data: doc.fields }
      }
      catch (error: any) {
        if (error?.status === 412) // changed since it was loaded: the contract's 409
          throw Object.assign(new Error('Changed by someone else'), { statusCode: 409, data: { currentVersion: error.data.revision } })
        throw error
      }
    },

    permissions: ref => api(`/permissions/${ref.name}`),
  })
}
```

It implements no `revisions`, so `capabilities.revisions` is `false` and the editor shows no history for it.

## The built-in adapters

- **`createDatabaseAdapter({ store, schema, permissions })`** from `#atelier/server`: the contract on your database, with revisions. `permissions` is required: it decides who may read and update what.
- **`createMemoryAdapter({ collections, singletons })`** from `nuxt-atelier/adapter`: keeps content in memory, implements only the required operations, and doesn't validate. It's a reference implementation, for demos and tests.

## Testing an adapter

Nuxt Atelier's contract test suite runs every required operation against an adapter, plus the optional ones it reports, and checks that `capabilities` matches what it implements. It's in the repository at [`test/adapter/contract.ts`](https://github.com/AnoRebel/nuxt-atelier/blob/main/test/adapter/contract.ts) and runs with Vitest: copy it into your tests and call it with a factory for your adapter.
