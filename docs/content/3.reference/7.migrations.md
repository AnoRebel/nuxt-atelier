---
title: Migrations
description: How schema changes reach your database, in development and in production.
---

Changing a field in a collection changes the tables behind it. Nuxt Atelier writes each change as a migration: a SQL file you review and commit with the schema change. Migrations live in `server/atelier/migrations/<engine>/`, one folder each.

## In development

`nuxt dev` keeps your database in step with the schema. When it starts, and whenever you save a collection or singleton file, it:

1. writes a migration for what changed, and logs its path;
2. applies it to your dev database.

Adding a field or a collection needs no other step. Commit the migration with your schema change.

Generating migrations needs `drizzle-kit`, an optional dev dependency (see [why](/getting-started/installation#why-drizzle-kit-is-optional)). Without it, `nuxt dev` still applies migrations that already exist, and logs how to install it.

### Removing or renaming a field

A migration that deletes data is never written silently. When you remove or rename a field (or a collection), `nuxt dev` applies nothing and logs what it needs to know:

```txt
The schema change would lose data, so no migration was written:
  drop column atelier_c_articles.summary: pass --drop articles.summary to delete its data,
  or --rename articles.summary=<new field> if it was renamed
```

Answer with one command:

::code-group
```bash [removed]
npx atelier migrate generate --drop articles.summary
```
```bash [renamed]
npx atelier migrate generate --rename articles.summary=teaser
```
::

A rename keeps the data; a drop deletes it. The migration records your decision at the top:

```sql [server/atelier/migrations/postgres/20261103170610_brave_lion/migration.sql]
-- atelier:confirm drop column atelier_c_articles.summary
ALTER TABLE "atelier_c_articles" DROP COLUMN "summary";
```

## Commands

| Command | Does |
|---|---|
| `atelier migrate generate` | writes a migration for schema changes. `--name`, `--drop`, `--rename` as above; `--dialect postgres` writes one for another engine than your dev database |
| `atelier migrate apply` | applies pending migrations to the database |
| `atelier migrate status` | lists applied and pending migrations |

Each takes `--root <dir>` for an app outside the current directory, and reads the database URL from `NUXT_ATELIER_DATABASE_URL` or your `nuxt.config.ts`.

`apply` refuses a migration that drops or renames something without its `-- atelier:confirm` line, including one written by hand. It names the line to add and runs nothing.

Generating and applying take a lock on the database, so `nuxt dev` and the `atelier` command on the same machine never migrate the same database at the same time.

## In production

Migrations are bundled into the build. When the server starts with migrations it hasn't applied:

- it logs which ones are pending;
- CMS writes answer `503` with the same list, until they're applied.

Apply them as a deploy step, before the new version takes traffic:

```bash
npx atelier migrate apply
```

Or let the server apply them when it starts:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  atelier: { migrations: { autoApply: true } },
})
```

`NUXT_ATELIER_MIGRATIONS_AUTO_APPLY=true` does the same at runtime. A deploy step is the safer choice when several instances start at once.

### Developing on SQLite, deploying on Postgres

Migrations are per engine. Generate the production engine's migrations alongside your dev ones; it needs no connection to that database:

```bash
npx atelier migrate generate --dialect postgres
```
