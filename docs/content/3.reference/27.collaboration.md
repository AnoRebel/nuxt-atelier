The admin keeps editors from overwriting each other and lets them discuss content in place. The database is the source of truth for all of it; the real-time connection only says what changed. For how it looks to editors, see [Working together](/guides/working-together).

## Edit locks and presence

While an entry is open in the admin, it sends a heartbeat every 20 seconds. The heartbeat marks the user as present, and takes or renews the entry's **edit lock** when the user may update it and was active within [`collaboration.idleTimeout`](/reference/configuration#collaboration). A lock that isn't renewed expires after `collaboration.lockTimeout` (60 seconds by default).

While someone else holds the lock, the entry is read-only in the admin, and the API refuses writes to it from anyone else (`PATCH`, publish and delete) with `423 locked`, API tokens included. Taking over a lock needs the `publish` permission on the type; the previous holder is notified.

| Request | What it does |
|---|---|
| `GET /api/_atelier/collab/<type>/<id>` | `{ lock, viewers }`: the lock (`userId`, `name`, `expiresAt`, `mine`) or `null`, and who has it open |
| `POST /api/_atelier/collab/<type>/<id>` | the heartbeat, `{ edit?, takeover? }`; answers the same, with `granted` |
| `DELETE /api/_atelier/collab/<type>/<id>` | closed: leaves, and gives the lock up |
| `GET /api/_atelier/collab/<type>/<id>/people` | who may read the entry, to mention |

A singleton's `<id>` is its name. Every request needs a signed-in user who may read the entry; other entries answer `404`.

## Comments

Comments belong to an entry, or one of its blocks, and form threads: a first comment and its replies. They're stored apart from content, so they're never published, versioned or exported with it, and they're deleted with their entry. Reading them needs the `read` permission; writing, replying and resolving need [`comment`](/reference/permissions#content-permissions). Users may edit and delete their own comments; deleting someone else's needs `delete` on the type.

| Request | Body | |
|---|---|---|
| `GET /api/_atelier/comments/<type>/<id>` | | every comment, oldest first, with `authorName` and `orphaned` (about a block that's no longer in the draft) |
| `POST /api/_atelier/comments/<type>/<id>` | `{ body, block?, thread?, mentions? }` | a comment on the entry, a block of it, or a reply to a thread |
| `PATCH /api/_atelier/comments/<type>/<id>/<comment>` | `{ body?, mentions? }` or `{ resolved }` | edits (its author), or resolves and reopens a thread (through its first comment) |
| `DELETE /api/_atelier/comments/<type>/<id>/<comment>` | | deletes it; a thread's first comment takes its replies |

`mentions` are user ids; only users who may read the entry are kept, and they're notified. A reply notifies the thread's author.

## Notifications

Mentions, replies and takeovers notify the user in the admin, and by email when [email is set up](#email).

| Request | |
|---|---|
| `GET /api/_atelier/notifications?unread=true&limit=50` | the signed-in user's, newest first: `{ items: [{ id, kind, data, readAt, createdAt }], unread }` |
| `POST /api/_atelier/notifications/read` | `{ ids? }`: marks these read, or all |

`kind` is `mention`, `reply` or `takeover`; `data` has the `type` and `entry`, who it's from (`by`, `byName`), and for comments the `comment`, `thread` and an `excerpt`.

## The real-time connection

With `collaboration.realtime: 'auto'` (the default), the module turns on Nitro's WebSocket support and serves `/api/_atelier/ws`. The admin opens it with a ticket from `POST /api/_atelier/collab/ticket`, good for a minute and for the site it was asked on, and follows topics: `entry:<type>:<id>` for an entry's lock, presence and comments, `user:<id>` for its own notifications. A topic is followed only when the user may read that entry on the ticket's [site](/reference/multi-site): the server keeps each site's topics apart (`entry:<site>:<type>:<id>`), so a connection hears nothing of another site. A change sends `{ topic, kind }`, and the admin refetches. The handshake is refused without a fresh ticket, and from another origin, so another site can't open it with an editor's cookies.

| Platform | Real-time |
|---|---|
| Node, Bun, Deno servers | pushed |
| Cloudflare Workers | pushed within an isolate; changes made through others arrive with the 60-second poll |
| Vercel, Netlify and other serverless platforms | polling |

Where it isn't available, with `realtime: false`, or while the connection is down, the admin polls every 20 seconds instead: the same changes appear, only later. While connected it still polls every 60 seconds, since pushes reach only the connections of the server instance where the change was made.

## Email

Notifications are emailed when there's somewhere to send them, set as a secret in `NUXT_ATELIER_MAIL_URL`, with the sender in [`mail.from`](/reference/configuration#mail) or `NUXT_ATELIER_MAIL_FROM`:

| URL | Sends through |
|---|---|
| `smtp://user:password@host:587`, `smtps://user:password@host:465` | SMTP, with [`nodemailer`](https://nodemailer.com) installed in your app (servers only, not Workers) |
| `resend://<api key>` | [Resend](https://resend.com)'s API |
| `postmark://<server token>` | [Postmark](https://postmarkapp.com)'s API |

Messages go out as [background jobs](/reference/jobs), retried with backoff when the provider fails. To send another way, register your own adapter in a server plugin:

```ts [server/plugins/mail.ts]
import { registerMailAdapter } from '#atelier/server'

export default defineNitroPlugin(() => {
  registerMailAdapter(() => ({
    async send({ from, to, subject, text, html }) {
      await myMailService.send({ from, to, subject, text, html })
    },
  }))
})
```

`sendMail({ to, subject, text, html? })` from `#atelier/server` queues your own messages through the same adapter; it answers `false` when email isn't set up.

## In your own admin screens

| Composable | What it gives you |
|---|---|
| `useAtelierPresence(target, canEdit)` | the heartbeat for `{ type, id }`: `lock`, `others` (viewers), `lockedByOther`, `takeover()` |
| `useAtelierComments(target)` | `threads` (with `replies`), `people` to mention, and the `add`, `resolve` and `remove` mutations |
| `useAtelierNotifications()` | `items`, `unread`, and `markRead(ids?)` |
| `useAtelierRealtime()` | `connected`, `pollInterval()`, and `follow(topic, listener)` |
