A block is a piece of a page, such as a hero, a card or a call to action, that editors add, order and fill in. A `blocks()` field holds a list of them. Each block is stored as data:

```json
{ "id": "b1", "type": "Hero", "props": { "title": "Welcome", "variant": "dark", "items": [] } }
```

Each block is backed by a Vue component, which can come from your app, a layer or a UI library. Atelier reads every block's schema at build time. The server uses it to validate saved content, and the editor will use it to build its forms. Public pages load only the block components they render, never the schemas.

## Rendering blocks

`<AtelierBlocks>` renders a list of blocks:

```vue [pages/[slug\].vue]
<script setup lang="ts">
const route = useRoute()
const { data } = await useAtelierEntry('pages', () => route.params.slug as string)
</script>

<template>
  <main>
    <AtelierBlocks :blocks="data?.data.content" />
  </main>
</template>
```

Each block's fields and options are passed to its component as props. Each nested area is passed as the slot of the same name (see [Areas](#areas-nesting-blocks)), so block components never import anything from Atelier to render.

## Writing a block in a `.vue` file

Put a component in `blocks/` (`app/blocks/` with Nuxt 4's directory layout) and call `defineBlock()` in its `<script setup>`. Its content fields are the [field helpers](/reference/fields) you pass to `defineProps`:

```vue [app/blocks/Hero.vue]
<script setup lang="ts">
import { defineBlock, select, text, textarea } from '#atelier'

defineBlock({
  label: 'Hero',
  group: 'layout',
  options: { variant: select({ options: ['light', 'dark'], default: 'light' }) },
  areas: { actions: { allow: ['Cta'], max: 2 } },
})

defineProps({
  title: text({ required: true, maxLength: 80 }),
  tagline: textarea(),
  variant: { type: String, default: 'light' },
})
</script>

<template>
  <section :class="`hero hero--${variant}`">
    <h1>{{ title }}</h1>
    <p>{{ tagline }}</p>
    <slot name="actions" />
  </section>
</template>
```

The field helpers are typed as Vue props: `title` is a `string` in the template, and `tagline` is `string | undefined`. Props that aren't field helpers, like `variant` here, stay ordinary props.

The block is named after its file: `Hero.vue` is `Hero`, and `pricing-table.vue` is `PricingTable`. Set `name` in `defineBlock()` to choose another name.

The build removes `defineBlock()` and the field helpers from the code the browser loads, and turns each helper into a plain prop with its default.

::warning
`defineBlock()` and the field helpers are read from the source, not run, so they take **literal values only**: strings, numbers, booleans, arrays, objects and other field helpers. A variable, function call or spread fails the build with the file, line and column.
::

::tip
If a prop has the same name as a helper you import, such as a `text` prop next to the `text()` helper, alias the import (`import { text as textField } from '#atelier'`). Otherwise the helper shadows the prop in your template's type checking.
::

## Writing a block in a `.block.ts` file

To use a component you can't or don't want to edit, such as one from a UI library, declare the block in a `*.block.ts` file next to your blocks and pass the component:

```ts [app/blocks/cta.block.ts]
import { defineBlock, select, text } from '#atelier'
import { UButton } from '#components'

export default defineBlock({
  component: UButton,
  label: 'Call to action',
  fields: { label: text({ required: true }), to: text({ required: true }) },
  options: { variant: select({ options: ['solid', 'outline'], default: 'solid' }) },
})
```

The fields become the component's props, so name them after its props. Here `label`, `to` and `variant` are props of Nuxt UI's `UButton`. The component can come from:

- `#components`, for anything Nuxt registers, including your own components and a UI module's;
- a relative path, such as `import Card from '../components/Card.vue'`;
- a package, such as `import { Button } from 'some-ui-library'`. Only the component you name is bundled, not the whole library.

When the component's props don't match the fields you want, write a small wrapper component and point the block at it.

## Block metadata

| Key | Meaning |
|---|---|
| `name` | the block's type name, in PascalCase; defaults to the file name |
| `label`, `description`, `icon` | how the editor shows the block |
| `group` | a group for the editor's picker and for area rules (`group:layout`) |
| `tags` | tags for area rules (`tag:heavy`) |
| `options` | presentation settings, such as variants or spacing (see below) |
| `areas` | nested block lists (see below) |
| `fields` | content fields, in `.block.ts` files only (`.vue` blocks use `defineProps`) |
| `component` | the component, in `.block.ts` files only |

## Options

`options` are for how a block looks, such as a color variant or a layout. `fields` are for what it says. Both are passed to the component as props and validated the same way. The editor shows options apart from content, so editors can change the look without wading through the copy.

## Areas: nesting blocks

An area is a list of blocks inside a block, such as the actions of a hero or the two sides of a columns block. Each area is rendered through the component's slot of the same name:

```vue [app/blocks/Columns.vue]
<script setup lang="ts">
import { defineBlock } from '#atelier'

defineBlock({
  label: 'Columns',
  areas: {
    left: { min: 1 },
    right: { deny: ['Columns'] },
  },
})
</script>

<template>
  <div class="columns">
    <div><slot name="left" /></div>
    <div><slot name="right" /></div>
  </div>
</template>
```

On public pages, an empty area passes no slot, so a block can leave out its wrapper with `v-if="$slots.right"`. In editing previews the slot is always there, so editors can drop blocks into it.

The rules an area can set:

| Rule | Meaning |
|---|---|
| `allow` | only these may be placed: block names, `group:<group>` or `tag:<tag>`; anything when omitted |
| `deny` | these may not be placed, with the same forms as `allow`; `deny` wins over `allow` |
| `min`, `max` | how many blocks the area must or may hold |
| `label` | how the editor names the area |

The server checks every blocks field at every depth whenever content is saved:

- each block's fields and options;
- which blocks each area allows, and how many it holds;
- that no block id is used twice;
- how deep blocks nest: [`limits.maxNestingDepth`](/reference/configuration) levels, 10 by default.

Errors name the area and the block, with the path to the problem:

```json
{ "path": "content.0.props.actions.0", "message": "\"Video\" can't be placed in area \"actions\" of Hero" }
```

A `blocks()` field's own `allow` lists the block names allowed at its top level.

## Overriding blocks from layers

Blocks are found in `blocks/` of your app and of every [layer](/getting-started/layer). If two of them use the same name, the one with higher priority wins: your app over its layers, and earlier layers over later ones. To change a layer's `Hero`, add your own `Hero.vue`. Content keeps working as long as its fields match.

Two blocks with the same name in the same layer fail the build with an error naming both files.

## Using any UI library

Blocks are ordinary components, so they work with any UI library or with none:

- **Nuxt UI:** wrap its components in `.vue` blocks (a hero around `UPageHero`, a card around `UCard`), or point a `.block.ts` file straight at one, like `UButton` above.
- **shadcn-vue:** its components are copied into your app. Use them in `.vue` blocks, or wrap one so its props match your fields. For example, a `CtaButton` can render `<Button as-child><NuxtLink :to="to">{{ label }}</NuxtLink></Button>`.
- **Tailwind CSS:** utility classes in your block templates.
- **Plain CSS:** `<style scoped>` in your block components.

The same content renders in each. As long as two sets of blocks share names and fields, you can switch UI libraries without touching saved content. Atelier's own tests render one page with all four.

## Previews

The visual editor needs to know which element belongs to which block and field. In an editing preview, `<AtelierBlocks>` adds `data-at-block` and `data-at-type` to each block's root element. Wrap a field's output in `<AtelierField>` to mark it as well:

```vue
<h1>
  <AtelierField name="title">{{ title }}</AtelierField>
</h1>
```

`<AtelierField>` renders a `<span>` by default; set `as` to render another element. These attributes appear only when `useAtelierPreview()` is `true`, which the editor's preview sets. Public pages never carry them.

## When blocks change

Content often outlives the code it was written for. Saved content stays loadable and saveable when:

- **a field or option is removed:** its value stays in the stored props and is ignored;
- **an area is added:** older blocks render it as empty;
- **a block type is removed:** `<AtelierBlocks>` skips those blocks with a console warning and renders the rest;
- **an `object` or `repeater` loses a sub-field:** the leftover key is kept. Unknown fields are refused only at the top level of an entry.

`findStaleContent()` lists what's out of date in an entry's data:

```ts
import { contentRepairs, findStaleContent } from '#atelier'

const stale = findStaleContent(fields, entry.data, blockSchemas)
// [{ kind: 'orphaned-prop', path: 'content.0.props.subtitle', blockId: 'b1', type: 'Hero', prop: 'subtitle', value: 'Hi' }, …]
```

| Kind | What it is |
|---|---|
| `orphaned-prop` | a block prop that no field, option or area of its block declares any more |
| `unknown-block` | a block whose type no longer exists |
| `missing-area` | an area added to a block's type since the block was saved |
| `orphaned-key` | a key left in an `object` or `repeater` item by a removed sub-field |

`contentRepairs` fixes one item at a time. Each repair returns new data and leaves its input unchanged:

```ts
let data = entry.data
data = contentRepairs.drop(data, stale[0]) // delete a stale prop, key or block
data = contentRepairs.move(data, stale[1], 'headline') // a renamed field: move the value to it
data = contentRepairs.addArea(data, stale[2]) // give the new area an empty list
```

`move` doesn't overwrite a value already in the new field. Save the repaired data as you would any other edit. The admin will list stale content and offer these repairs.

::note
Fields made with [`defineFieldType()`](/reference/fields#custom-field-types) can't be used in blocks yet. Those types are defined in server code, which isn't read when blocks are read at build time.
::
