Three built-in collections hold what editors reuse. `atelier-templates` is always there; `atelier-shared-blocks` and `atelier-patterns` are added when the app has [blocks](/reference/blocks). Their tables come with your next `atelier migrate generate`. Like any collection, they're edited through the [content API](/reference/content-api) and the admin, and [roles](/reference/permissions) grant them by name.

## Shared blocks

A shared block (`atelier-shared-blocks`: `title`, and `block`, a list of exactly one block) is placed on pages by reference:

```json
{ "id": "cta", "type": "atelier:shared", "props": { "ref": "<shared block id>" } }
```

- **Reads** replace each reference with the shared block's content in the same stage: its published version on the site, its draft in drafts and previews. The block keeps the reference's `id`, gets `shared: "<ref>"`, and its nested blocks' ids are prefixed with the reference's id (`cta:…`), so a block placed twice on a page keeps ids unique. A reference to a shared block that isn't published, or no longer exists, stays as it is, and `<AtelierBlocks>` skips it.
- **Saving** a block with `shared` stores the reference again, so content read from the API saves back unchanged. A block without `shared` is the page's own: dropping the mark **detaches** it.
- **Validation** places a reference as the block type it stands for (an area's `allow` and `deny`), and refuses one to a shared block that doesn't exist (`422`). A shared block can't contain references.
- **Usage** is kept like relations: `GET /api/_atelier/shared-blocks/<id>/usage` answers `[{ type, id, field }]`, drafts and live pages alike.
- **Deleting** one that's used answers `409 referenced`. `POST /api/_atelier/shared-blocks/<id>/release` with `{ mode: 'detach' }` puts a copy of its content in place of every reference (pages look the same), `{ mode: 'remove' }` drops them; both change drafts and live pages in place, without new versions, and need `delete` on shared blocks and `update` on the types that use it. Then it can be deleted.

## Patterns

Patterns are block arrangements inserted as independent copies. Define the app's in `server/atelier/patterns.ts` (a layer's are merged, the app's win by name):

```ts [server/atelier/patterns.ts]
import { definePatterns } from '#atelier/server'

export default definePatterns({
  pricing: {
    label: 'Pricing section',
    description: 'Three plans and a question',
    blocks: [
      { id: 'p1', type: 'PricingPlans', props: { plans: [] } },
      { id: 'p2', type: 'Faq', props: { items: [] } },
    ],
  },
})
```

Editors save more in `atelier-patterns` (`title`, `description`, `blocks`). `GET /api/_atelier/patterns` lists both, `[{ id, label, description, source: 'code' | 'saved', blocks }]`, with fresh block ids on every request: what's inserted doesn't link back.

## Entry templates

A collection's `templates` are starting points for new entries:

```ts [server/atelier/collections/pages.ts]
export default defineCollection({
  fields: { title: text({ required: true }), content: blocks() },
  templates: {
    landing: { label: 'Landing page', data: { title: 'New landing page', content: [{ id: 'h', type: 'Hero', props: {} }] } },
  },
})
```

Editors save more from existing entries into `atelier-templates` (`title`, `description`, `type`, `data`). `GET /api/_atelier/templates/<collection>` lists both for those who may create entries there, `[{ id, label, description, source, data }]`, blocks with fresh ids; create the entry with that `data`.
