`@nuxt-atelier/admin` adds the admin to your app at `/admin` (the core's `admin.base`). Without it, everything else works the same: the content API, pages and blocks.

```bash
bun add @nuxt-atelier/admin
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-atelier', '@nuxt-atelier/admin'],
})
```

The first visit shows the setup screen, which creates the first administrator. After that, the admin asks people to sign in.

## How it sits in your app

- **Client-side only.** The admin isn't rendered on the server, and it's sent with `X-Robots-Tag: noindex, nofollow`.
- **Isolated styles.** The admin renders in its own shadow root, over the page. Your site's CSS can't reach it, and its CSS never reaches your pages: it adds no stylesheet, UI module or Tailwind to your app.
- **Your app's pages are untouched.** The route is marked `meta.atelier = 'admin'`, so your own route middleware can skip it.

## Look and feel

The admin is built on [crystal-neuo](https://github.com/AnoRebel/crystal-neuo). Each person picks their appearance in the **Appearance** dialog (the palette button, or Alt+Shift+A), and it's remembered in their browser:

| Setting | Choices |
|---|---|
| Material | refraction, tactile, signal, folio, bloom, hybrid |
| Theme | system, light, dark, high contrast |
| Density | compact, comfortable, spacious |
| Platform | web, iOS, Android, Windows, macOS, or match this device |
| Glass | frost, rim light, reduce transparency |
| Layout | sidebar or top bar; a floating, icons-only or attached sidebar; contained or full width |

### Branding and defaults

Set your name, logo, favicon, token overrides and the appearance people start with in app config. Changes need no rebuild of the admin:

```ts [app/app.config.ts]
export default defineAppConfig({
  atelierAdmin: {
    name: 'Acme CMS',
    logo: '/logo.svg',
    favicon: '/admin-icon.svg',
    // crystal-neuo tokens, applied inside the admin only, in every theme: with a brand colour, set the text
    // colour that reads on it too, at 4.5:1 or more
    tokens: { '--accent-primary-base': '#c2410c', '--content-on-accent': '#ffffff' },
    // until someone picks their own in the Appearance dialog
    appearance: { material: 'folio', nav: 'top', density: 'compact' },
  },
})
```

## Replace a part of the admin

Put a component in `app/atelier-admin/` (in your app or in a layer) named after the part, and the admin uses it instead. Your app's file wins over a layer's.

| File | Replaces |
|---|---|
| `Home.vue` | the dashboard |
| `CollectionList.vue`, `EntryEdit.vue` | a collection's list, the edit form (props: `name`, and `kind` and `id` for the form) |
| `Users.vue`, `Roles.vue`, `RoleEdit.vue` | user and role screens |
| `SignIn.vue`, `Setup.vue`, `NotFound.vue` | sign-in, first-run setup, the not-found and not-allowed view |
| `Brand.vue` | the name or logo in the sidebar and on sign-in (prop: `compact`) |
| `Field<Type>.vue` | the input of every field of that type: `FieldDate.vue`, `FieldRelation.vue`, `FieldGeoPoint.vue` for a custom `geo-point` type |

A field input gets `modelValue`, `field` (its definition), `label`, `error` and `disabled`, and emits `update:modelValue`:

```vue [app/atelier-admin/FieldDate.vue]
<script setup lang="ts">
defineProps<{ modelValue?: string | null, label?: string, error?: string, disabled?: boolean }>()
defineEmits<{ 'update:modelValue': [value: string] }>()
</script>

<template>
  <label class="cn-field">
    <span class="cn-field__label">{{ label }}</span>
    <input class="cn-input" type="date" :value="modelValue ?? ''" :disabled="disabled" @input="$emit('update:modelValue', ($event.target as HTMLInputElement).value)">
    <span v-if="error" class="cn-field__message">{{ error }}</span>
  </label>
</template>
```

Components render inside the admin's shadow root, so style them with crystal-neuo's classes (`cn-…`) and tokens (`var(--content-primary)`), not with your site's CSS. A custom field type's own `input` component (see [fields](/reference/fields)) is rendered there too.

## Your own admin pages

Add pages with the module's `pages` option. They appear in the navigation for those allowed to open them; anyone else gets a "You can't open this" view at their address.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-atelier', '@nuxt-atelier/admin'],
  atelierAdmin: {
    pages: [{
      path: 'newsletter',             // /admin/newsletter
      label: 'Newsletter',
      icon: 'mail',                   // a Lucide icon, bundled at build time
      group: 'Marketing',             // default "Tools"
      order: 10,
      requires: 'settings',           // admin areas the user must manage (any one of them)
      component: '~/admin/Newsletter.vue',
    }],
  },
})
```

Plugins add theirs with the `atelier:admin:pages` build hook:

```ts
nuxt.hook('atelier:admin:pages', (pages) => {
  pages.push({ path: 'reports', label: 'Reports', component: resolve('./runtime/Reports.vue') })
})
```

### Overlays of other libraries

A component that portals its overlays (a date picker, a menu, a modal) to `document.body` puts them outside the admin, where they're unstyled. Pass the admin's portal as the target instead; in development the admin warns when an overlay lands on `<body>`:

```vue
<script setup lang="ts">
const portal = useAtelierAdminPortal()
</script>

<template>
  <Teleport :to="portal">
    <div role="dialog">…</div>
  </Teleport>
</template>
```

More icons for content types' `admin.icon`: list them in `atelierAdmin.icons` (Lucide names, like `newspaper`).

## Build your own admin

The admin's logic is in auto-imported composables, independent of its look, so you can build screens, or a whole other admin, on the same behavior:

| Composable | What it gives you |
|---|---|
| `useAtelierAdmin()` | the base path, `to(...segments)` for admin links, and `api(path, options)` for the CMS API (with the CSRF header) |
| `useAtelierSession()` | `user`, `loading`, `setupNeeded`, and the `signIn`, `signOut` and `createAdmin` mutations |
| `useAtelierAdminSchema()` | the content types the user may read, with their fields, what the user may do, the blocks and locales (`GET /api/_atelier/schema`) |
| `useAtelierPermissions()` | `can(action, type)`, `ownOnly(action, type)`, `manages(area)`, `canWrite(type, field)` |
| `useAtelierNavigation()` | the navigation items: dashboard, collections, singletons, areas and your pages |
| `useAtelierCollection(name)` | a list's `state` (page, size, sort, search, filter, columns), `entries`, `total`, bulk `publish`, `unpublish` and `remove` (failures reported per entry), `exportEntries` |
| `useAtelierEntryForm({ kind, name, id? })` | a [TanStack Form](https://tanstack.com/form) validated with the server's own field rules, `submit()`, `publish`, `unpublish`, `remove`; server errors land on their fields, and a save someone else overtook is refused |
| `useAtelierUsers()`, `useAtelierRoles()` | users and roles, with their mutations |

They run on [TanStack Query](https://tanstack.com/query): the admin page provides its client, so use them inside the admin (your pages and overrides).
