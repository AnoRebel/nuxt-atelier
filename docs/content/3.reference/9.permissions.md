title: Permissions
description: Roles, what they allow, and checking them in your own server code.
---

Every user has one **role**. A role lists what its users may do with each collection and singleton, and which admin areas they manage. One check, `can()`, applies it everywhere: the API, the admin and the visual editor.

## The admin role

`admin` is built in and can do everything. It can't be defined or edited, and the CMS never lets the last administrator lose it (see [Authentication](/reference/authentication#users)).

## Visitors

Visitors who aren't signed in have the `public` role on the content API. They can only read, and only what's [published](/reference/content-api#drafts-and-publishing). By default, `public` reads every collection and singleton. Define a role named `public`, in code or in the admin, to narrow it:

```ts [server/atelier/roles.ts]
export default defineRoles({
  public: { content: { '*': { actions: ['read'], hidden: ['internalNotes'] }, orders: { actions: [] } } },
})
```

Its write permissions, if you give it any, are ignored: visitors can't write. The `public` role can't be given to a user.

## Defining roles

Roles come from two places:

- **The admin**, by users whose role manages `roles`. These are stored in the database.
- **Code**, in `server/atelier/roles.ts` of your app or a layer, for teams that keep roles in git. These are read-only in the admin, and replace a database role with the same name.

```ts [server/atelier/roles.ts]
import { defineRoles } from '#atelier/server'

export default defineRoles({
  author: {
    label: 'Author',
    content: {
      articles: { actions: ['create', 'read', 'update', 'delete', 'publish'], ownOnly: ['update', 'delete', 'publish'] },
      '*': { actions: ['read'] },
    },
  },
  reviewer: {
    label: 'Reviewer',
    capabilities: ['media'],
    content: {
      '*': { actions: ['read', 'update'], readOnly: ['slug'], hidden: ['internalNotes'] },
    },
  },
})
```

First-run setup adds an `editor` role to the database when none exists: every action on all content, plus media.

### A role

| Key | What it does |
|---|---|
| `label` | the name shown in the admin |
| `capabilities` | admin areas the role manages: `users`, `roles`, `settings`, `media`, `redirects` |
| `content` | permissions per collection or singleton name; `'*'` covers every one without its own entry |

An entry in `content` replaces `'*'` for that name; it isn't merged with it.

### Content permissions

| Key | What it does |
|---|---|
| `actions` | what the role may do: `create`, `read`, `update`, `delete`, `publish`, and `comment` (write [comments](/reference/collaboration#comments) in the admin) |
| `ownOnly` | of those, the ones allowed only on entries the user created (`read`, `update`, `delete`, `publish`) |
| `hidden` | top-level fields the role can neither read nor write |
| `readOnly` | top-level fields the role can read but not change |

A role that can `update` but not `publish` saves drafts; publishing is refused with a `403`. `update` also lets a role read drafts (`?draft=true`) and an entry's history.

::warning
The `roles` capability lets a user edit any database role, including their own: treat it as close to administrator. `users` is safer: someone with it can't grant the admin role, change an administrator, or change their own role.
::

## Checking permissions in server code

`useAtelierPolicy()` returns the policy for the current roles. It's rebuilt on each call, so a role edited in the admin applies at once, on every server.

```ts [server/api/articles/[id]/feature.post.ts]
import { requireUser, useAtelierPolicy } from '#atelier/server'

export default defineEventHandler(async (event) => {
  const user = await requireUser(event) // 401 when signed out
  if (!(await useAtelierPolicy()).can(user, 'publish', 'articles'))
    throw createError({ status: 403, message: 'Your role can\'t publish articles' })
  // …
})
```

| Function | Returns |
|---|---|
| `can(user, action, resource, entry?)` | whether `user` may do a content action on a collection or singleton. For an `ownOnly` action, pass the entry; without it, `can()` answers whether the action is possible on some entries |
| `can(user, 'manage', capability)` | whether the user's role manages an admin area |
| `ownOnly(user, action, resource)` | whether `action` is limited to the user's own entries, to filter lists |
| `fields(user, resource)` | `{ hidden, readOnly }`, the field names as sets |
| `readable(user, resource, data)` | entry data without the hidden fields |
| `unwritable(user, resource, data, before?)` | the fields a write would change that the role can't write |

`requireUser(event, capability?)` throws a `401` when nobody is signed in, and with a capability, a `403` unless the role has it.

`createPolicy(roles)` is also exported from `#atelier` for app code, for example to hide buttons. The server always checks again.
