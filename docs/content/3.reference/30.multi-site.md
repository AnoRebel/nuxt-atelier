---
title: Multi-site
description: Several sites from one deployment, each with its domains, content, media and editors.
---

One app can serve several sites: a brand's shops in different countries, a company's product sites. Each site has its own host names, entries, singletons, URLs, media, redirects, sitemap, robots rules, search, forms and API tokens, and editors reach only the sites they're given. Without `sites`, there's one site and none of this shows: no site columns, no switcher, nothing to configure.

## Setting up

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-atelier', '@nuxt-atelier/admin'],
  atelier: {
    locales: { codes: ['en', 'de', 'fr'] },
    sites: {
      main: { hosts: ['example.com', 'www.example.com'], label: 'Example' },
      shop: { hosts: ['shop.example.com'], label: 'Shop', locales: ['de', 'fr'], defaultLocale: 'de' },
    },
    fallbackSite: 'main', // for hosts no site has: local development, health checks
  },
})
```

| Option | |
|---|---|
| `sites.<name>.hosts` | the host names it's served at (a port allowed: `localhost:3000`); each belongs to one site |
| `sites.<name>.label` | its name in the admin |
| `sites.<name>.locales`, `defaultLocale` | its locales, some of `locales.codes` |
| `fallbackSite` | serves a request whose host is no site's; without it, such requests answer 404 (health checks always answer) |

Then generate a migration (`atelier migrate generate`): site-scoped tables get their site column, which every row needs. Set up `sites` before there's content; in an app with content already, edit the generated migration to give the existing rows their site (add the column with that site as its default, then drop the default) before you apply it.

## Which site a request is for

The `Host` header picks it (behind a proxy that sets `X-Forwarded-Host`, with [`auth.trustProxy`](/reference/configuration#auth)). Signed-in tools, like the admin's site switcher, can name another with an `x-atelier-site` header; access checks then apply as for that site. Server code reads it with `useAtelierSite(event)`.

## Content: per site, or shared

Collections and singletons belong to a site unless they say otherwise:

```ts [server/atelier/collections/tags.ts]
export default defineCollection({
  scope: 'shared', // every site sees the same tags
  fields: { name: text({ required: true }) },
})
```

- A **site's** entry is invisible from any other site: reads answer 404, and writes, publishing, history and deletes find nothing to change. Unique fields and URLs are unique per site, so two sites can both have `/about`.
- A **shared** type's entries are the same on every site; its URLs are served on every site.
- A **singleton** has a copy per site, unless it's shared.

Every data access in server code names its site, so forgetting one is a type error, not a leak:

```ts [server/api/latest.get.ts]
import { queryEntries, useAtelierEntries, useAtelierSite } from '#atelier/server'

export default defineEventHandler(async (event) => {
  const entries = await useAtelierEntries(useAtelierSite(event)) // this request's site
  return queryEntries(event, 'articles', { limit: 5 }) // the request, or a site, comes first
})
```

`useAtelierMedia`, `useAtelierSettings`, `useAtelierTokens`, `searchSite` and the [hooks](/reference/hooks)' `site` follow the same rule. `allSites()` lists them all, for jobs that cover every site; `singleSite` is the one site of an app without `sites`.

## Per site

| | |
|---|---|
| **Media** | each site has its own library; an item uploaded with `shared` is in every site's. A site's file isn't served on another site's host. |
| **Redirects** | per site |
| **Sitemap and robots.txt** | per site, at each host: the sitemap lists that site's pages (and shared types'), with its own host in the URLs; robots rules set in the admin are that site's |
| **Search** | finds that site's entries and shared ones |
| **Forms** | forms are content of a site; their submissions, exports and erasure requests stay within it |
| **API tokens** | work only on the site they were made on |
| **Revisions, comments, locks** | follow their entry |

## Editors and sites

Administrators reach every site. Everyone else reaches the sites they have a role on, with that role there: an editor on one site can be a reviewer on another, or nothing at all. On a site without a role, a signed-in user is a visitor: published content only, and `403` from the admin and its API.

Assign site roles in the admin (Users, a user's **Sites**) or with `PUT /api/_atelier/users/<id>/sites` and `{ sites: { shop: 'editor' } }` (the `users` capability). The roles themselves are the app's roles, the same on every site.

In the admin, a user who reaches several sites picks one with **Site** in the top bar; it's remembered in their browser. One admin, at any of the hosts, manages every site the user may reach.

## Deploying with several domains

- Point every site's domains at the one deployment; it decides by host. Behind a CDN or proxy, forward the host (`X-Forwarded-Host`) and turn on `auth.trustProxy`.
- `NUXT_PUBLIC_ATELIER_SITE_URL` doesn't apply with sites: URLs in sitemaps, feeds and emails use the host the request came to.
- Sign-in cookies belong to the host they were set on: editors sign in at the host they use for the admin, and switch sites there.
- Prerendering and static hosting serve one host: multi-site needs the server.
