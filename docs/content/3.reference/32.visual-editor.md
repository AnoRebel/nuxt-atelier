The visual editor is `@nuxt-atelier/editor`, a page of the [admin](/reference/admin). It opens an entry's real page in a frame and edits it there: blocks selected, added, moved and edited in place, with undo, a command palette, reusable content and comments. For editors, see [The visual editor](/guides/visual-editor).

## Installing

```bash
bun add @nuxt-atelier/editor
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-atelier', '@nuxt-atelier/admin', '@nuxt-atelier/editor'],
  atelierEditor: {
    // the widths to preview at; a custom width is always offered
    presets: [{ label: 'Desktop', width: 1280 }, { label: 'Tablet', width: 768 }, { label: 'Mobile', width: 375 }],
  },
})
```

It needs the admin, and works on collections and singletons with a [route](/reference/routing): their entries' forms get a **Visual editor** button, which opens `/admin/edit?type=<type>&id=<id>`. Editing there takes permission to update the entry.

## Making blocks editor-friendly

Blocks work in the editor as they are. In an editing preview, `<AtelierBlocks>` marks each block's root element with `data-at-block` and `data-at-type`, and the editor finds blocks by those marks. A few things make them better to edit.

**Mark fields to edit in place.** Wrap a text field's output in `<AtelierField>`, and give `<AtelierRichText>` the field it shows:

```vue [app/blocks/Feature.vue]
<script setup lang="ts">
import { defineBlock, richText, text } from '#atelier'

defineBlock({ label: 'Feature' })
defineProps({ heading: text({ required: true }), body: richText() })
</script>

<template>
  <section>
    <AtelierField name="heading" as="h2">{{ heading }}</AtelierField>
    <AtelierRichText :value="body" field="body" />
  </section>
</template>
```

`name` and `field` are the block's field, or the entry's own when the element isn't inside a block: a layout can mark the page's title the same way. Text fields become editable as plain text, rich-text fields in Tiptap with the admin's formatting; both write to the same form and undo history as the side panel. The marks appear only in an editing preview.

**Render an element.** A block whose component renders nothing (a teaser list with nothing to list) gets a dashed stand-in in the preview, so it can still be selected. A block that renders a comment node or plain text gets one too: give the component a root element when you can.

**Proxy mode, for blocks that show part of their content.** A carousel showing one slide, tabs showing one panel: its other blocks are on the page but out of sight, so they can't be clicked or dropped on. Opt the block into proxy mode:

```vue [app/blocks/Carousel.vue]
<script setup lang="ts">
import { defineBlock } from '#atelier'

defineBlock({ label: 'Carousel', areas: { slides: { label: 'Slides', allow: ['Slide'] } }, editor: { proxy: true } })
</script>
```

In the preview, the block is replaced by a plain box with its label and each area's blocks one after another, rendered by their own components. They're selected, edited, dragged and dropped on like any other. Public pages render the block as written.

## Extending the editor

Plugins and apps add commands to the editor's command palette (Ctrl+K) with `addEditorCommands` from `#atelier-editor`, in a client plugin:

```ts [app/plugins/editor-commands.client.ts]
import { addEditorCommands } from '#atelier-editor'

export default defineNuxtPlugin(() => {
  addEditorCommands(editor => [{
    id: 'shop:clear-badges',
    label: 'Remove the sale badges',
    group: 'Shop',
    run: () => {
      const data = editor.data()
      editor.setData({ ...data, content: (data.content as { type: string }[]).filter(b => b.type !== 'SaleBadge') })
    },
  }])
})
```

The function is called each time the palette opens, so it can offer commands that depend on the selection. `editor` has:

| | |
|---|---|
| `selected`, `select(id)` | the selected block's id, and selecting another (`null`: none) |
| `insert(type)` | inserts a new block of that type after the selection, if it may go there (`false` if not) |
| `data()`, `setData(data)` | the entry's data as edited, and replacing it: one undoable step, shown in the page at once |
| `undo()`, `redo()`, `save()` | as the buttons |

Prefix ids with your plugin's name. A command's errors are shown to the editor as a message.

## How the editor reaches the page

The page in the frame is the site's own route, rendered by your app, so it looks exactly as published. To make it editable without touching what visitors get:

1. The editor asks `POST /api/_atelier/editor/token` with `{ type, id }`. For someone who may update that entry, the answer is a token, signed with a key derived from `NUXT_APP_SECRET` and good for two minutes, and the URL to open: the entry's path with `?_atelier=edit&_atelier_token=…`.
2. The page's client plugin sees `_atelier=edit` in a frame and exchanges the token at `POST /api/_atelier/editor/session` for an HTTP-only `atelier-edit` cookie, bound to the signed-in user and the site, for eight hours. Reloads check it with `GET` instead.
3. Only then does it load the bridge, a separate chunk. The page renders drafts and gets the editor's marks. Without a valid session, the same URL is the public page, and the bridge is never downloaded: visitors' pages carry nothing of the editor but this check of the query.

The editor's chrome lives in the admin's shadow root, so neither the site's CSS nor the editor's reaches the other. The page draws nothing of its own: selection boxes, drop lines and comment markers are drawn over the frame by the editor, from the positions the page reports.

## The bridge protocol

The editor and the page talk with `postMessage`, on the site's own origin. Each side accepts a message only from that origin, from the window it expects (the frame, or its parent), and of the protocol's shape; anything else is ignored. Every message carries `version: 1`. The schemas are in `#atelier/shared/bridge`.

From the editor to the page:

| `type` | Fields | |
|---|---|---|
| `atelier:state` | `id`, `data` | the entry's data as edited: the page renders it (an entry's id, or a singleton's name) |
| `atelier:select` | `id` | the selected block (or `null`): scrolled into view |

From the page to the editor:

| `type` | Fields | |
|---|---|---|
| `atelier:ready` | | the bridge listens: send the state |
| `atelier:geometry` | `blocks`, `fields`, `viewport` | where every block (`{ id, type, rect, placeholder? }`) and marked field (`{ path, rect }`) is, in the frame's viewport; sent at most once a frame, after any change of layout, scroll or size |
| `atelier:select` | `id` | a block was clicked (links aren't followed) |
| `atelier:hover` | `id` | the pointer is over a block (or `null`) |
| `atelier:inline` | `path`, `value` | a field edited in place: `path` is `<field>` or `<block id>/<field>`; `value` its text, a rich-text document, or `null` |
| `atelier:key` | `key`, `shift` | Ctrl/⌘ with `k`, `z` or `y` pressed while the page has focus, for the editor's shortcuts |

While something is edited in place, the page holds back incoming state until editing ends, so the caret doesn't move under the typist.

In-place rich text is loaded through the `#atelier-inline-rich` alias: none in `nuxt-atelier`, Tiptap from `@nuxt-atelier/editor`. It's imported on the first double click on a rich-text field, in an edit session only.
