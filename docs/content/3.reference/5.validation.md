title: Validation
description: Field rules, custom validators and the errors they produce.
---

Every write is validated on the server against the fields, whatever sent it. The admin uses the same rules, so editors see problems before they save.

## Rules

| Rule | Applies to | Fails when |
|---|---|---|
| `required: true` | every field | the value is missing, `null`, `''` or an empty list |
| `minLength`, `maxLength` | `text`, `textarea`, `email`, `url`, `slug` | the text is too short or too long |
| `pattern` | `text` | the whole value doesn't match the regular expression |
| `min`, `max` | `number` | the number is outside the range |
| `minItems`, `maxItems` | `multiSelect`, `relation` with `many`, `repeater`, `blocks` | the list has too few or too many items |
| `unique: true` | top-level fields | another entry already has the value |

Fields that aren't `required` accept an empty value; their other rules apply once there is one.

`pattern` is a string, so definitions stay serialisable. Give `patternMessage` to tell editors what's expected:

```ts
text({ pattern: '[A-Z]{3}-\\d{4}', patternMessage: 'use the form ABC-1234' })
```

## Custom validators

`validate` takes any [Standard Schema](https://standardschema.dev): Valibot, Zod, ArkType and others. It runs after the field's own rules, on the server only:

```ts
import * as v from 'valibot'

number({ validate: v.pipe(v.number(), v.check(n => n % 5 === 0, 'use a multiple of 5')) })
```

## Errors

A rejected write lists every failing field with its path and reason. Paths use dots, with list positions as numbers:

```json
[
  { "path": "title", "message": "required" },
  { "path": "faq.1.question", "message": "required" },
  { "path": "faq.2.meta.order", "message": "expected a whole number" }
]
```

Nothing is saved when any field fails.
