Your content's structure lives in code. Nuxt Atelier builds storage, validation, the admin forms and TypeScript types from it.

## Collections and singletons

- A **collection** holds many entries of one type: articles, products, team members.
- A **singleton** holds exactly one entry (per locale): site settings, the header, the footer.

Each is a file. The file name is its name:

```txt
server/atelier/
├── collections/
│   ├── articles.ts      → the "articles" collection
│   └── authors.ts
└── singletons/
    └── settings.ts      → the "settings" singleton
```

Names use lowercase letters, digits and `-`, starting with a letter.

```ts [server/atelier/collections/articles.ts]
import { defineCollection, relation, richText, select, slug, text } from '#atelier/server'

export default defineCollection({
  labels: { singular: 'Article', plural: 'Articles' },
  route: { pattern: '/blog/{slug}' },
  fields: {
    title: text({ required: true, maxLength: 120 }),
    slug: slug({ from: 'title', required: true, unique: true }),
    status: select({ options: ['draft', 'published'], default: 'draft' }),
    body: richText(),
    author: relation({ to: 'authors' }),
  },
})
```

```ts [server/atelier/singletons/settings.ts]
import { defineSingleton, media, text } from '#atelier/server'

export default defineSingleton({
  label: 'Site settings',
  fields: {
    siteName: text({ required: true, default: 'My site' }),
    logo: media({ accept: ['image/*'] }),
  },
})
```

### Collection options

| Option | What it does |
|---|---|
| `fields` | the fields of each entry (see [Fields](/reference/fields)) |
| `labels` | `{ singular, plural }` names shown in the admin |
| `route` | entries get URLs and are served by the site (see [Routing](/reference/routing)) |
| `localized` | entries have one version per locale, linked as translations (see [Localization](/reference/localization)) |
| `versioned` | drafts and publishing: saves change a draft, and the site serves the version last published (see [Drafts and publishing](/reference/content-api#drafts-and-publishing)). Without it, every save is published at once. Every type keeps a revision history either way. |
| `admin` | `{ icon, group, columns }`: how the collection appears in the admin |
| `renamedFrom` | the collection's previous name, after a rename (see [Renaming](#renaming)) |

Singletons take `fields`, `label`, `route`, `versioned` and `admin` (`icon`, `group`). They can't be `localized` yet: for content translated per locale, use a localized collection holding one entry.

## Renaming

A field's key and a collection's name are what its data is stored under. Rename one and declare its previous name with `renamedFrom`, so the data moves with it:

```ts [server/atelier/collections/articles.ts]
export default defineCollection({
  fields: {
    teaser: textarea({ renamedFrom: 'summary' }), // was `summary`
  },
})
```

```ts [server/atelier/collections/posts.ts]
export default defineCollection({
  renamedFrom: 'articles', // this file was articles.ts
  fields: { /* … */ },
})
```

The next migration renames the column or table instead of dropping it, and updates the relations and history that name it. In `nuxt dev` that happens as soon as you save. Without `renamedFrom`, a rename looks like a removal, and [no migration is written](/reference/migrations#removing-or-renaming-a-field) until you confirm it.

Singleton data moves on its next save; until then it's read from the old key. Only top-level fields can be renamed: a nested field is stored inside its parent's JSON.

You can remove `renamedFrom` once every database you deploy to has the migration.

## Layers

Nuxt Atelier also reads `server/atelier/collections/` and `server/atelier/singletons/` in every [Nuxt layer](https://nuxt.com/docs/getting-started/layers) your app extends, so a layer can ship ready-made content types. When the app and a layer define the same name, the app's definition wins (and between layers, the one with higher priority).

## In development

Edit a definition and the change applies right away. Adding or deleting a definition file restarts the Nuxt dev server, so the new content type is registered.

## Types

Entry types are inferred from your definitions, on the server and in your app:

```ts
import type { CollectionEntry, SingletonEntry } from '#atelier' // or '#atelier/server'

type Article = CollectionEntry<'articles'>
// { title: string, slug: string, status?: 'draft' | 'published' | null, body?: RichTextDocument | null, author?: string | null }

type Settings = SingletonEntry<'settings'>
```

Fields with `required: true` are always present; the others may be missing or `null`. Change a field and the types follow; there's nothing to regenerate.
