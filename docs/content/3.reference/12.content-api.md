title: Content API

Every collection and singleton gets REST endpoints under `/api/_atelier`. The admin uses them, your app can, and so can anything else with an [API token](#api-tokens). Every request is checked against the caller's [permissions](/reference/permissions).

To query content from your own Nuxt code, the [typed helpers](/reference/querying#typed-helpers) are simpler.

## Collections

| Request | Does |
|---|---|
| `GET /api/_atelier/collections/<name>` | a page of entries; see [Querying content](/reference/querying) |
| `POST /api/_atelier/collections/<name>` | `{ data, publish? }`: creates an entry |
| `GET /api/_atelier/collections/<name>/<id>` | one entry; `?depth=1` populates relations, `?fields=title,date` selects fields |
| `PATCH /api/_atelier/collections/<name>/<id>` | `{ version, data, publish? }`: updates an entry |
| `DELETE /api/_atelier/collections/<name>/<id>` | deletes an entry, applying its relations' [`onDelete`](/reference/fields#when-the-referenced-entry-is-deleted) |
| `POST /api/_atelier/collections/<name>/<id>/publish` | `{ version }`: publishes the draft (versioned collections) |
| `POST /api/_atelier/collections/<name>/<id>/unpublish` | takes the entry off the site; its draft stays |
| `GET /api/_atelier/collections/<name>/<id>/revisions` | its saved versions, newest first: `[{ version, createdAt, authorId, published }]` |
| `GET /api/_atelier/collections/<name>/<id>/revisions/<version>` | one saved version, with its `data` |
| `POST /api/_atelier/collections/<name>/<id>/revisions/<version>/restore` | `{ version }`: saves that version's data as the next draft |

An entry:

```json
{
  "id": "9b2e…",
  "version": 3,
  "createdAt": "2026-11-03T09:30:00.000Z",
  "updatedAt": "2026-11-05T14:02:11.000Z",
  "createdBy": "a71c…",
  "publishedVersion": 3,
  "data": { "title": "Hello", "category": "news", "author": "4f0d…" }
}
```

A list:

```json
{ "items": [ … ], "total": 42, "limit": 20, "next": "WyJIZWxsbyIsIjliMmUuLi4iXQ" }
```

### Updating

`PATCH` merges `data` into the stored data: send only the fields that change. Fields you can't see or change keep their values.

`version` is the version you read. If someone saved a newer one since, the update is refused with `409` and `currentVersion`, instead of overwriting their change: reload, reapply, and save again.

### Drafts and publishing

In a [`versioned`](/reference/content-schema#collection-options) collection, writes change the entry's **draft**, and the site serves the version last **published**:

- Reads return what's published, to everyone: an entry that was never published, or was unpublished, answers `404`. Lists and filters see the published values too, and the [routes endpoint](#routes) resolves published URLs.
- Add `?draft=true` to read drafts instead. It needs the `update` permission on the type (that's the preview permission); for anyone else, the flag is ignored and they get what's published.
- `publishedVersion` is the version the site serves, or `null`. When it's below `version`, the draft has changes that aren't published yet.
- `POST …/publish` with the draft `version` you read publishes it: a new version, marked `published` in the history, live at once. A newer draft answers `409`. A URL or `unique` value another published entry still has answers `422`, as does an entry nested under a parent that isn't published.
- `publish: true` on a create or update saves and publishes in one step.
- `POST …/unpublish` takes the entry off the site. Its URLs answer `404` and don't redirect; its draft stays.
- Publishing and unpublishing need the `publish` permission, and are recorded in the [audit log](/reference/authentication#the-audit-log) as `entry.published` and `entry.unpublished`.

A changed URL [redirects](/reference/routing#redirects) when the change is published, not when the draft is saved.

### History and restore

Every save and publish adds a version to the entry's history, in every collection: `{ version, createdAt, authorId, published }`, newest first. Versions are never changed or removed by a save.

Restoring (`POST …/revisions/<version>/restore`, with the draft `version` you read) saves that version's data as a new draft. The versions in between stay in the history, and nothing is published until you publish. Fields your role can't see or change keep their current values. A version saved under an older schema is validated like any save, so a field that's now required may need a value first (`422`).

To show what changed between two versions, `diffEntries(before, after)` (from `#atelier` and `#atelier/server`) compares their `data`. Blocks are matched by id, wherever they are:

```ts
const [older, newer] = await Promise.all([3, 4].map(v => $fetch(`/api/_atelier/collections/pages/${id}/revisions/${v}`)))
diffEntries(older.data, newer.data)
// [{ kind: 'field', path: 'title', before: 'About', after: 'About us' },
//  { kind: 'moved', block: 'b7', type: 'Quote', from: { at: { field: 'content' }, index: 3 }, to: { at: { parent: 'b2', area: 'items' }, index: 0 } },
//  { kind: 'changed', block: 'b1', type: 'Hero', prop: 'title', before: 'Hi', after: 'Hello' }]
```

The kinds are `field` (a field outside blocks, with a dot path into objects), `added`, `removed`, `moved` and `changed` (one prop of a block). A block moved when it changed area, or order among the blocks it shares a list with; blocks shifted by an insertion didn't.

Collections that aren't versioned publish every save; they have no publish or unpublish endpoints (`422`).

## Singletons

| Request | Does |
|---|---|
| `GET /api/_atelier/singletons/<name>` | the singleton; before its first save, its field defaults with `version: null` |
| `PATCH /api/_atelier/singletons/<name>` | `{ version, data, publish? }`, merged; `version` is `null` for the first save |
| `POST /api/_atelier/singletons/<name>/publish` | `{ version }`: publishes the draft (versioned singletons) |
| `POST /api/_atelier/singletons/<name>/unpublish` | takes it off the site |
| `GET /api/_atelier/singletons/<name>/revisions` | saved versions, newest first |
| `GET /api/_atelier/singletons/<name>/revisions/<version>` | one saved version |
| `POST /api/_atelier/singletons/<name>/revisions/<version>/restore` | `{ version }`: saves that version's data as the next draft |

## Routes

`GET /api/_atelier/routes?path=/about` returns the entry served at a site path, for [routable](/reference/routing) collections and singletons:

```json
{
  "path": "/about", "locale": "", "kind": "collection", "name": "pages", "id": "8f1c…",
  "component": null, "layout": null, "blocks": ["content"],
  "entry": { "id": "8f1c…", "version": 3, "path": "/about", "data": { "title": "About", … } }
}
```

It takes `locale` (for [per-locale patterns](/reference/routing#a-pattern-per-locale)), `depth` and `draft`. With `draft=true`, someone who can edit the type also gets drafts, at their draft URL. The caller needs permission to read the entry, as for its own endpoint. A path no published entry has answers `404`.

## Who can do what

- Signed out, reads use the [`public` role](/reference/permissions#visitors), which reads everything published by default. Every other request answers `401`.
- Each operation needs its [permission](/reference/permissions): `read` to read, `create`, `update`, `delete`, `publish`. Revision history needs `update`, since it holds drafts.
- Fields the caller can't read are left out of every response, including in populated relations. A related entry from a collection the caller can't read stays an id.
- Writing a field the caller can't change answers `403`, naming the fields in `data.fields`.
- With an own-entries-only permission, lists show only the caller's entries, and other entries answer `403`.
- Writes (create, update, delete, publish, unpublish) are limited per user or token to `limits.writesPerMinute` (default 120); then `429` with `Retry-After`.

Page size is capped by `limits.maxPageSize` (default 100), and `depth` by `limits.maxRelationDepth` (default 3).

## API tokens

API tokens let a static site build, a mobile app or another service use the content API without a user account. Administrators create them:

```bash
curl -X POST https://example.com/api/_atelier/tokens \
  -H 'content-type: application/json' -H "cookie: $SESSION" -H "x-atelier-csrf: $CSRF" \
  -d '{ "name": "Static site build", "expiresAt": "2027-06-30T00:00:00Z" }'
```

The response has the token, `atk_…`, shown only this once; store it as a secret. Use it as a bearer token:

```bash
curl https://example.com/api/_atelier/collections/articles -H "authorization: Bearer $ATELIER_TOKEN"
```

- **Permissions:** without `permissions`, a token can only read. To allow more, give it [content permissions](/reference/permissions#content-permissions), as in a role: `{ "articles": { "actions": ["create", "read"], "hidden": ["internalNotes"] } }`.
- **Reach:** tokens work on the content API only. They can't manage users, roles, tokens or the audit log.
- **Storage:** tokens are stored as SHA-256 hashes, so the database never holds a usable token.
- **Revoking:** `DELETE /api/_atelier/tokens/<id>`. A revoked or expired token answers `401`.
- **Listing:** `GET /api/_atelier/tokens` lists tokens, never their secret, with when each was last used.

Creating and revoking tokens are recorded in the [audit log](/reference/authentication#the-audit-log).

## Errors

Errors are Nuxt's error responses, with a machine-readable `code` under `data`, and details where there are any:

```json
{
  "statusCode": 422,
  "message": "Invalid entry: title: required; views: expected 0 or more",
  "data": {
    "code": "validation_failed",
    "errors": [
      { "path": "title", "message": "required" },
      { "path": "views", "message": "expected 0 or more" }
    ]
  }
}
```

| Status | `code` | When | Details |
|---|---|---|---|
| 400 | `bad_request` | the request is malformed | |
| 400 | `invalid_query` | a filter or sort names a field or operator the collection can't use | |
| 401 | `unauthenticated` | signed out, or an invalid, expired or revoked token | |
| 403 | `forbidden` | the caller's permissions don't allow it | `fields`: fields they can't change |
| 403 | `csrf` | a cross-site request, or a missing `x-atelier-csrf` header | |
| 404 | `not_found` | no such collection, entry or version | |
| 405 | `method_not_allowed` | | |
| 409 | `conflict` | someone saved a newer version | `currentVersion` |
| 409 | `referenced` | a delete refused by a relation that restricts it | `references` |
| 409 | `last_admin`, `setup_done`, `already_exists` | from [user management and setup](/reference/authentication) | |
| 422 | `validation_failed` | the data or request body doesn't validate | `errors`: `[{ path, message }]` |
| 429 | `rate_limited` | too many writes or sign-ins | `Retry-After` header |
| 501 | `unsupported` | the database can't do it (an import on Cloudflare D1) | |
| 503 | `migrations_pending` | the database needs migrations | `pending` |

Your own server routes can answer in the same shape with `apiError(status, message, details?, code?)` from `#atelier/server`.

## OpenAPI

`GET /api/_atelier/openapi.json` returns an OpenAPI 3.1 description of the content API for your schema: every collection and singleton, a JSON Schema per field, the error shape and both ways to authenticate. Administrators only. Load it in Swagger UI, Scalar or a client generator.
