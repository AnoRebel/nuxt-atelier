Nuxt Atelier stores content in your own database. Pick the engine with a URL; everything else behaves the same on every engine.

## Engines

| Engine | URL | Install |
|---|---|---|
| SQLite (local file) | `file:.data/atelier.sqlite` (the default) | nothing |
| libSQL / Turso | `libsql://my-db.turso.io?authToken=…` | nothing |
| PostgreSQL | `postgres://user:password@host:5432/db` | `pg` |
| MySQL | `mysql://user:password@host:3306/db` | `mysql2` |
| MariaDB | `mariadb://user:password@host:3306/db` | `mysql2` |
| Cloudflare D1 | `d1:<binding>` | nothing, see [Cloudflare D1](/deployment/cloudflare-d1) |

Set the URL in `nuxt.config.ts`, or at runtime with an environment variable, which needs no rebuild:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-atelier'],
  atelier: {
    database: { url: 'postgres://cms@localhost:5432/atelier' },
  },
})
```

```bash [.env]
NUXT_ATELIER_DATABASE_URL=postgres://cms:secret@db.internal:5432/atelier
```

A build includes the drivers your app has installed. To switch a built app to another engine, install that engine's driver and rebuild. Changing the URL to another database of the same engine needs no rebuild.

::note
A relative SQLite path is relative to your app's root for `nuxt dev` and the `atelier` command, and to the working directory of a built server. The default keeps the file in `.data/`, which Nuxt's `.gitignore` already excludes.
::

## Connection settings

- **Pool size:** `limits.dbPoolSize` (default 10) caps the connections to Postgres, MySQL and MariaDB.
- **SQLite concurrency:** a write waits up to 5 seconds for another one to finish instead of failing. A dev server and the `atelier` command can share a database file.
- **Errors:** when the database can't be reached, the error names the engine and the URL, with the password replaced by `***`.

## Creating the tables

Tables come from your [content schema](/reference/content-schema) through migrations. In `nuxt dev` they're created and updated for you. See [Migrations](/reference/migrations) for how that works and how production gets them.

## Reading and saving content

Server code reads and saves entries with `useAtelierEntries()`:

```ts [server/api/articles/[id].put.ts]
import { assertMigrated, toHttpError, useAtelierEntries } from '#atelier/server'

export default defineEventHandler(async (event) => {
  await assertMigrated()
  const { version, data } = await readBody(event)
  const entries = await useAtelierEntries()
  return entries.save('articles', { id: getRouterParam(event, 'id'), version, data })
    .catch((error) => { throw toHttpError(error) })
})
```

| Method | Does |
|---|---|
| `get(collection, id)` | an entry with its relations, or `undefined` |
| `save(collection, { id?, version?, data })` | creates an entry (no `id`) or updates one (`id` and the `version` it was read at) |
| `getSingleton(name)` | a singleton's data, or `undefined` before its first save |
| `saveSingleton(name, { version, data })` | saves a singleton; `version` is `null` for its first save |
| `revisions(collection, id)` | the saved versions of an entry, newest first |

Every save:

- **validates** the data against the schema, including `unique` fields, and writes nothing if a field fails;
- **is atomic:** the entry, its relations and a revision snapshot are saved together, or not at all;
- **checks the version:** a save based on an older version than the one stored is refused instead of overwriting someone else's changes.

`toHttpError` turns the failures into responses that keep their details:

| Status | When | `data` |
|---|---|---|
| 409 | someone saved a newer version | `{ currentVersion }` |
| 422 | the data doesn't validate | `{ errors: [{ path, message }] }` |
| 404 | the entry or collection doesn't exist | |
| 503 | the database has [pending migrations](/reference/migrations#in-production) (from `assertMigrated`) | |
