The CMS signs people in through an **auth adapter**. The built-in one keeps email and password users in your database; [Better Auth](/reference/auth-adapters#better-auth) adds OAuth, two-factor and more; or [write your own](/reference/auth-adapters#writing-an-auth-adapter). Roles and [permissions](/reference/permissions) work the same with all of them.

## The session secret

Sessions are sealed with a secret derived from Nuxt's `runtimeConfig.appSecret`. Set it in production, at least 32 characters:

```bash [.env]
NUXT_APP_SECRET=a-long-random-string-of-at-least-32-characters
```

Changing it signs everyone out.

## The built-in adapter

- **Passwords** are hashed with scrypt (N=2^17, r=8, p=1). On runtimes without scrypt, such as edge functions, PBKDF2-SHA256 with 600,000 iterations. The hash records its settings, so a stronger default later upgrades each password the next time its user signs in.
- **Sessions** last 7 days, in an HTTP-only, `Secure`, `SameSite=Lax` cookie, sealed so its contents can't be read or changed. The server keeps only a hash of each session's id, so signing out ends a session for good, even if its cookie was copied.
- **A password change** signs the user out everywhere.

### Endpoints

| Endpoint | Does |
|---|---|
| `POST /api/_atelier/auth/login` | `{ email, password }`: signs in, returns the user |
| `POST /api/_atelier/auth/logout` | signs out |
| `GET /api/_atelier/auth/me` | `{ user }`: the signed-in user, or `null` |

A wrong password and an unknown email get the same `401`, so the response doesn't reveal who has an account.

### Sign-in limits

After 10 failed sign-ins for an email from one IP address within 15 minutes, further attempts get `429` with a `Retry-After` header until the window ends, even with the right password. An email alone allows five times as many, so switching addresses doesn't help. The counters are in the database, so every server instance shares them.

| Option | Default |
|---|---|
| `auth.signInAttempts` | `10` |
| `auth.signInWindow` | `900` (seconds) |
| `auth.trustProxy` | `false`: take the client IP from `X-Forwarded-For` |

Turn on `auth.trustProxy` only behind a proxy that sets `X-Forwarded-For` itself. Otherwise clients could send any address and get a fresh limit each time.

## Passkeys

Passkeys let users sign in with their device's fingerprint, face or PIN instead of a password. They're off by default:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  atelier: { auth: { passkeys: true } },
})
```

```bash
npm i @simplewebauthn/server
```

- A signed-in user adds a passkey; the password stays as the way back in.
- The passkey belongs to your site's domain, from `NUXT_PUBLIC_ATELIER_SITE_URL`. Set it in production: without it, the domain is taken from each request, which is meant for development.
- Every sign-in asks the device to verify the user, and a passkey whose counter goes backwards (a cloned key) is refused.
- When passkeys are off, their endpoints answer `404` and none of their code is in your build.

| Endpoint (under `/api/_atelier/auth/passkeys`) | Does |
|---|---|
| `POST /register-options`, `POST /register` | adds a passkey for the signed-in user |
| `POST /login-options`, `POST /login` | signs in with a passkey |
| `GET /` | the signed-in user's passkeys |
| `DELETE /<id>` | removes one of them |

Passkeys belong to the built-in adapter. With Better Auth, use [its passkey plugin](/reference/auth-adapters#better-auth).

## First-run setup

While there are no users, `POST /api/_atelier/setup` with `{ email, name?, password }` creates the first administrator, adds an `editor` role and signs them in. `GET /api/_atelier/setup` returns `{ needed }`. Once any user exists, setup answers `409`, for good.

## Users

`/api/_atelier/users` manages users, for roles with the `users` capability:

| Request | Does |
|---|---|
| `GET /api/_atelier/users` | every user |
| `POST /api/_atelier/users` | `{ email, name?, role, password? }` |
| `PATCH /api/_atelier/users/<id>` | `{ email?, name?, role?, password? }` |
| `DELETE /api/_atelier/users/<id>` | |

It refuses to demote or delete the last administrator, with `409`. Only administrators can grant the admin role or change an administrator, and nobody can change their own role.

Roles are managed at `/api/_atelier/roles` (`GET`, `PUT /<name>`, `DELETE /<name>`), for roles with the `roles` capability. Roles defined in code can't be changed there.

## The audit log

Security-relevant events are recorded with who did them, to what, when and from which IP:

- first-run setup;
- sign-ins, failed sign-ins and sign-outs;
- passkeys added and removed;
- users created, changed (with the old and new email, name or role) and deleted;
- roles saved and deleted, with the old and new definition.

Passwords are never recorded; a change shows as `password: 'changed'`. Administrators read the log at `GET /api/_atelier/audit`, newest first, with `limit` (at most 200), `before` (the `at` of the last entry of the previous page) and `action`.

Record your own events from server code:

```ts
import { audit } from '#atelier/server'

await audit(event, { action: 'entry.published', actorId: user.id, target: { type: 'articles', id } })
```

## Calling the API from your own code

Requests that change something (`POST`, `PUT`, `PATCH`, `DELETE`) to `/api/_atelier/` are checked against cross-site request forgery:

- a browser's `Sec-Fetch-Site` must be `same-origin`, and its `Origin` your site's;
- a signed-in request sends the session's token in an `x-atelier-csrf` header. The token is in the `atelier-csrf` cookie, which your scripts can read:

```ts
const token = document.cookie.match(/(?:^|; )atelier-csrf=([^;]+)/)?.[1]
await $fetch('/api/_atelier/roles/writer', { method: 'PUT', body: { label: 'Writer' }, headers: { 'x-atelier-csrf': token } })
```

The admin does this for you. Scripts outside a browser send no cookies, so the token doesn't apply to them.
