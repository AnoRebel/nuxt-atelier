Work that shouldn't hold up a request, or that has to happen later, goes in the job queue: scheduled publishing, revision cleanup, webhooks, your own tasks. The queue lives in your database (`atelier_jobs`), so jobs survive restarts and deploys.

## Defining and queueing jobs

Register a handler from a server plugin, and queue jobs from anywhere on the server:

```ts [server/plugins/jobs.ts]
import { defineJob } from '#atelier/server'

export default () => {
  defineJob<{ email: string }>('newsletter:welcome', async ({ email }) => {
    await sendWelcome(email) // throw to fail the attempt
  })
}
```

```ts
const jobs = await useAtelierJobs()
await jobs.enqueue('newsletter:welcome', { email }, { runAt: tomorrow, maxAttempts: 3, key: `welcome:${email}` })
```

| Option | Default | What it does |
|---|---|---|
| `runAt` | now | when the job is due |
| `maxAttempts` | `5` | attempts before it's kept as failed |
| `key` | none | at most one job per key: queueing again replaces it, and `jobs.cancel(key)` removes it |

A payload is JSON. Name jobs with a prefix of your own; `atelier:` is for Nuxt Atelier's.

A job that runs on its own every so often takes `every`, in milliseconds. One of it is kept queued under its name: it runs when the queue is first drained, then `every` after each success.

```ts
defineJob('reports:daily', sendReport, { every: 24 * 3600_000 })
```

## Retries

A job that throws is tried again later: after 30 seconds, then 1, 2, 4 minutes, doubling up to an hour between attempts. After `maxAttempts` it stays in the queue as `failed`, with the last error, until someone retries it:

| Request | Does |
|---|---|
| `GET /api/_atelier/jobs?status=failed` | jobs, newest first; `status` is `queued`, `running` or `failed` |
| `POST /api/_atelier/jobs/<id>/retry` | queues a failed job again, from its first attempt |

Both are for administrators. A job with no registered handler fails the same way, naming the job.

Each job is run by one runner, however many servers drain the queue at once. A runner that dies mid-job leaves it locked for 5 minutes; then another takes it, as a new attempt. So a job can run twice in rare cases: make handlers safe to repeat.

## When jobs run

The `atelier:jobs` Nitro task runs due jobs, `limits.jobConcurrency` at a time (4 by default). `jobs.schedule` says when, as a cron expression; every minute by default:

| Platform | How it runs |
|---|---|
| Node, Bun, Deno servers | Nitro's scheduler, in the server process |
| Vercel | a [Vercel Cron Job](https://vercel.com/docs/cron-jobs) calling the trigger endpoint, added to the build output. Set `CRON_SECRET` and `NUXT_ATELIER_JOBS_SECRET` to the same value. Vercel's Hobby plan runs crons at most daily. |
| Cloudflare Workers | a Cron Trigger, added to the `wrangler.json` Nitro generates (`nitro.cloudflare.deployConfig`). With your own wrangler config, add `jobs.schedule` to its `triggers.crons`. |
| Anything else | an external scheduler calling the trigger endpoint |

`jobs.schedule` takes 5 fields, or 6 with seconds first on servers. Set it to `false` to run jobs only through the trigger endpoint.

### The trigger endpoint

For platforms without scheduled tasks, have any scheduler call:

```bash
curl -X POST https://example.com/api/_atelier/jobs/run -H "Authorization: Bearer $NUXT_ATELIER_JOBS_SECRET"
```

It answers `404` until `NUXT_ATELIER_JOBS_SECRET` is set, and `401` for a wrong secret. It starts jobs for `jobs.triggerBudget` seconds (25 by default, under most platforms' request limits), then answers `{ ran, failed, remaining }`; jobs it didn't reach stay queued for the next call.

In development, Nitro runs the task by hand at `/_nitro/tasks/atelier:jobs`.
