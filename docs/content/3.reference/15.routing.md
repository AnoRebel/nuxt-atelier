title: Routing
description: Give collections and singletons URLs, and let the site serve their entries without writing a page for each.
---

A collection or singleton with a `route` is **routable**: each entry gets a URL, and the site serves it there.

```ts [server/atelier/collections/pages.ts]
import { blocks, defineCollection, slug, text } from '#atelier/server'

export default defineCollection({
  route: { pattern: '/{slug}' },
  fields: {
    title: text({ required: true }),
    slug: slug({ from: 'title', required: true }),
    content: blocks(),
  },
})
```

Save a page with the slug `about`, and `/about` shows it. Change the slug, and the page moves.

## Patterns

A pattern is the URL with `{field}` where a field's value goes: `/blog/{slug}`, `/events/{date}-{slug}`, or `/` for a singleton home page.

- A placeholder must be a **required top-level** `text`, `slug`, `number`, `select` or `date` (in `date` mode) field, so every entry has a URL.
- Each value fills one path segment. Characters that aren't allowed in a URL are percent-encoded, a `/` included.
- The fixed parts may hold letters, digits, `-`, `_`, `.` and `~`. A pattern starts with `/` and has no trailing `/`.
- Patterns under paths Nuxt serves itself (`/api`, `/_nuxt`, `/_…`) are refused.

A pattern that breaks a rule fails when the schema loads, naming the collection and the problem.

### A pattern per locale

Translate the fixed parts by giving one pattern per locale, the default locale first:

```ts
route: { pattern: { en: '/projects/{slug}', et: '/projektid/{slug}' } },
```

The entry is then served at `/projects/<slug>` and at `/projektid/<slug>`.

### Unique URLs

Two entries can't have the same URL. Saving one that would is refused with a `422` on the placeholder's field:

```json
{ "path": "slug", "message": "The URL /about is already used by entry \"8f1c…\" in \"pages\"" }
```

A per-locale pattern's URLs only conflict within their locale. A shared pattern's conflict with every locale's.

### Nested URLs

Pages often sit under other pages: `/services/design` under `/services`. Give the route a `parent`, the key of a relation to the same collection:

```ts [server/atelier/collections/pages.ts]
export default defineCollection({
  route: { pattern: '/{slug}', parent: 'parent' },
  fields: {
    title: text({ required: true }),
    slug: slug({ from: 'title', required: true }),
    parent: relation({ to: 'pages' }),
  },
})
```

An entry's URL is then its parent's URL followed by its own pattern. A page without a parent is at the top.

- **URLs move with their parent.** Rename `services` to `what-we-do`, and `/services/design` becomes `/what-we-do/design`, at every depth. The entries below don't get new versions: only their URLs change.
- **A move that would collide is refused.** If an entry below would land on a URL that's taken, the save is refused with a `422` naming that entry.
- **No cycles.** An entry can't be placed under itself or under an entry below it.
- **Old URLs keep working.** See [Redirects](#redirects).

With per-locale patterns, each locale's URL goes under the parent's URL in that locale.

## Entries carry their URL

Entries of routable types have a `path`, wherever they're read: from the API, in lists, and as populated relations. Listing cards can link to entries without building their URLs:

```vue
<NuxtLink v-for="post in data.items" :key="post.id" :to="post.path">
  {{ post.data.title }}
</NuxtLink>
```

With per-locale patterns, `path` is the default locale's URL and `paths` holds every locale's: `{ en: '/projects/harbour', et: '/projektid/harbour' }`.

## How entries are rendered

Atelier adds one catch-all page to your app. It ranks below every page of your own, so a page you write always wins over an entry with the same URL.

By default it renders the entry's `blocks()` fields with [`<AtelierBlocks>`](/reference/blocks), in your default layout. A type can choose its own component and layout:

```ts
route: { pattern: '/projects/{slug}', component: 'ProjectPage', layout: 'wide' },
```

`component` is the name of a global component (in `components/global/`, or registered with `global: true`). It gets the entry as its `entry` prop:

```vue [app/components/global/ProjectPage.vue]
<script setup lang="ts">
defineProps<{ entry: { path: string, data: { name: string } } }>()
</script>

<template>
  <article>
    <h1>{{ entry.data.name }}</h1>
  </article>
</template>
```

### Your pages come first

When a page of your app and an entry have the same URL, your page is served. That includes dynamic pages: `pages/[section]/old.vue` takes `/projects/old` from a project with the slug `old`. If your app has its own catch-all page (`pages/[...slug].vue`), it takes every URL, and no entry is served.

The API tells you which entries that happens to. A hidden entry's responses list the URLs a page hides, and the page's route path, so the admin can warn about them:

```json
{ "id": "8f1c…", "path": "/contact", "shadowed": [{ "path": "/contact", "page": "/contact" }], "data": { … } }
```

`shadowed` is left out when no page hides the entry.

A URL no entry has shows your app's 404 error page. So does an entry the visitor can't read, so the response doesn't tell whether one exists there.

::note
The catch-all is only added to apps that use pages (an `app/pages/` directory, or `pages: true`). An app with only an `app.vue` has no router, and stays that way.
::

To look up the entry at a path yourself, use the [routes endpoint](/reference/content-api#routes).

## Redirects

Redirects send visitors from one URL to another before anything renders. They're checked on every `GET` and `HEAD` request for a site path (not `/api` or `/_…`), from a list cached in memory.

### When an entry's URL changes

Rename an entry's slug, or move a page in a [nested route](#nested-urls), and its old URL redirects to the new one with a `301`, for the entry and every entry below it. Redirects to the old URL are pointed at the new one, so visitors never go through a chain. If an entry later takes a URL back, the redirect from it is removed: an entry's URL always wins.

Turn this off for a type with `route: { …, redirects: false }`.

### Managing redirects

Users whose role has the `redirects` capability (editors do, by default) manage them through the API, and soon the admin:

```http
POST /api/_atelier/redirects
{ "source": "/blog/:slug", "target": "/news/:slug", "status": 308 }
```

| Field | What it is |
|---|---|
| `source` | a path, or a pattern: `:name` stands for one segment, and a final `*` for the rest (`/docs/*`) |
| `target` | a path on the site, or a full `http(s)://` URL. It can use the source's `:name`s and `*` |
| `status` | `301` (the default), `302`, `307` or `308` |

The query string of the request is kept. An exact source wins over a pattern, and patterns are tried oldest first.

A redirect is refused with a `422` when:

- it would make a loop, through patterns too: `This would make a loop: /news/x → /blog/x → /news/x`;
- its source already redirects, or is an entry's URL;
- its target isn't a site path or an `http(s)` URL.

`GET`, `PATCH /<id>` and `DELETE /<id>` list, change and delete redirects. Each change is recorded in the [audit log](/reference/authentication#the-audit-log).

::note
A redirect never sends a visitor to another site by accident. A `Location` is never protocol-relative (`//host`), so a path like `/go//evil.example` matching `/go/*` → `/*` isn't redirected. Only a full URL an administrator entered leaves the site, and a request can't change its host.
::

With several server instances, a redirect changed on one reaches the others within 30 seconds.
