---
title: Localization
description: "Content in several languages: locales, translated and shared fields, translations, and fallbacks."
---

A localized collection keeps one version of each entry per locale. The versions are linked as **translations** of each other, and each one is an entry of its own: it has its own drafts, revisions, URL and publish state, so the German version can go live before the French one exists.

## Locales

List the locales in `nuxt.config.ts`:

```ts
export default defineNuxtConfig({
  atelier: {
    locales: {
      codes: ['en', 'de', 'de-at', 'fr'],
      default: 'en', // the first code when omitted
      fallback: { 'de-at': ['de'] }, // every other locale falls back to the default
    },
  },
})
```

| Option | What it does |
|---|---|
| `codes` | the content locales, as codes like `en` or `pt-br`. `['en']` by default |
| `default` | the locale of new entries when none is given, and the last fallback |
| `fallback` | where reads look when content is missing in a locale, in order. The default locale always comes last |

With one locale, nothing about localization shows in the admin.

## Localized types

Declare a collection `localized`. Fields are translated unless marked `shared`: a shared field has one value for every locale.

```ts [server/atelier/collections/products.ts]
export default defineCollection({
  localized: true,
  route: { pattern: '/products/{slug}' },
  fields: {
    slug: slug({ required: true, unique: true }),
    title: text({ required: true }),
    description: richText(),
    sku: text({ shared: true }),
    price: number({ shared: true }),
  },
})
```

- **Shared fields** are kept the same in every translation. Saving a new `sku` on the German version saves it on the English and French ones too, each getting a new version in its history. In a [versioned](/reference/content-api#drafts-and-publishing) type it changes their drafts; each goes live when that version is published.
- **Unique fields** are unique within a locale: the English and German versions may have the same slug.
- **URLs:** each version has the URL of its own locale. A pattern every locale shares (`/products/{slug}`) gives each version its path in its locale, so `/products/chair` can be the English chair and the German one. Resolve a path with its locale (`/api/_atelier/routes?path=…&locale=de`) to get the right one.

Singletons can't be localized yet. For translated site-wide content, use a localized collection with one entry.

## Translations

Create the first version of an entry as usual: it's in the default locale, or the one you give.

```ts
const chair = await $fetch('/api/_atelier/collections/products', {
  method: 'POST',
  body: { data: { slug: 'chair', title: 'Chair', sku: 'C-1' }, locale: 'en' },
})
```

Translate it with `POST …/<id>/translations`. The new version starts as a copy of the original's data, with your changes on top, and is linked to it:

```ts
const stuhl = await $fetch(`/api/_atelier/collections/products/${chair.id}/translations`, {
  method: 'POST',
  body: { locale: 'de', data: { title: 'Stuhl' } },
})
// { id: '…', locale: 'de', translations: { en: '<chair id>', de: '<stuhl id>' }, data: { slug: 'chair', title: 'Stuhl', sku: 'C-1' }, … }
```

Each version lists all of them in `translations`, by locale. A locale that already has a version is refused (`422`), as is one that isn't in `locales.codes` (`400`). Deleting a version deletes only that one; the others stay linked.

## Reading a locale

Pass `locale` to read the versions in that locale:

```ts
// the German products
await queryEntries('products', { locale: 'de' })
// the German version of this entry (any version's id works)
await getEntry('products', chair.id, { locale: 'de' })
```

In the REST API it's the `locale` query parameter, and `useAtelierQuery` and `useAtelierEntry` take it too. Without it, a list returns the default locale's versions, and an entry is read as stored, the way editors work on it.

When content is missing, the read follows the locale's fallback chain: `de-at`, then `de`, then the default.

- **A missing version:** reading an entry in a locale it has no version in returns the version in the first locale of the chain that has one. Its `locale` says which.
- **Empty fields:** translated fields left empty are filled from the versions further down the chain. `fallbacks` names each field filled this way, with the locale it came from.

```json
{ "id": "…", "locale": "de", "fallbacks": { "description": "en" }, "data": { "title": "Stuhl", "description": { … } } }
```

Use `fallbacks` to mark untranslated text, or to tell search engines a page isn't fully translated.

A list in a locale holds the entries that have a version in it, with their empty fields filled the same way. Entries without a version in that locale aren't listed.

## Localized URLs with an i18n module

The CMS stores each version's path without a locale prefix: `/produkte/stuhl` for the German chair. When the site uses an i18n module, its pages follow that module's locales and URL strategy, so the German chair is served at `/de/produkte/stuhl`:

| Module | How it's used |
|---|---|
| [nuxt-i18n-micro](https://github.com/s00d/nuxt-i18n-micro) | by default, when it's installed |
| [@nuxtjs/i18n](https://i18n.nuxtjs.org) | when nuxt-i18n-micro isn't installed |
| neither | locales come from the `locale` query parameter only (`/api/_atelier/routes?path=…&locale=de`) |

The module's `locales`, `defaultLocale` and `strategy` are read when the app builds. With `prefix_except_default` (both modules' default), `/products/chair` is the English version and `/de/produkte/stuhl` the German one. A version only answers under its own locale's prefix: `/produkte/stuhl` without `/de` is a 404. Content that isn't localized is served under every locale's prefix.

To pick a module when both are installed, set `atelier.i18n.module` to `'nuxt-i18n-micro'` or `'@nuxtjs/i18n'` (`false` ignores both), or add its adapter package after the modules:

```ts
export default defineNuxtConfig({
  modules: ['nuxt-atelier', '@nuxtjs/i18n', '@nuxt-atelier/i18n-nuxtjs'],
})
```

Keep the CMS's `locales.codes` and the module's locales the same codes.

Links to entries need the prefix too. `useAtelierLocalePath()` adds it as the module's strategy wants:

```vue
<script setup lang="ts">
const localePath = useAtelierLocalePath()
</script>

<template>
  <NuxtLink :to="localePath(entry.path, 'de')">Deutsch</NuxtLink>
</template>
```

::note
**nuxt-i18n-micro and Nuxt 5.** Under `future: { compatibilityVersion: 5 }`, nuxt-i18n-micro 3.30 doesn't build: its server code imports `useRuntimeConfig` from `#imports`, which Nuxt 5 behaviour no longer provides there. A CI job tracks this. Until it passes, use @nuxtjs/i18n in apps that opt into Nuxt 5 behaviour. If nuxt-i18n-micro isn't ready when Nuxt 5 ships, @nuxtjs/i18n becomes the default.
::
